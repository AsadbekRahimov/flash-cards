## Аудит запросов к БД и оптимизация горячих экранов ✅ код (2026-11-13)

**Запрос владельца (13.11.2026):** «полный анализ запросов к базе — их может быть больше, чем нужно, из-за этого падает RPS — и оптимизация».

**Как искали (не на глаз, а замером).**
- **Опись всех HTTP-запросов тестами.** Весь набор Pest (6,4 тыс. тестов, sqlite и PostgreSQL 16) с временным слушателем `DB::listen`: по каждому из ~6,5 тыс. HTTP-вызовов — маршрут, число запросов, точные повторы (тот же SQL и те же значения), число транзакций и savepoint. Слушатель в репозиторий не попал.
- **Объём.** `perf:seed --learners=50000 --members=400` (2,3 млн строк) на PostgreSQL 16.15 с настройками прода (`random_page_cost=1.1`, `jit=off`), `pg_stat_statements` с учётом времени планирования, `PERF_MEASURE=1 pest --group=perf`; плюс ученики с 2 000 и 8 000 начатых слов (в наборе `perf:seed` максимум 300).
- **Индексы.** Все 895 разных SQL из описи прогнаны через `EXPLAIN (GENERIC_PLAN)` на этом объёме: последовательных сканов больших таблиц на горячих путях нет (единственные — пул дистракторов пробного экзамена, см. «Не сделано»).

**Что показал аудит.**
- **Лишних запросов и N+1 на горячих путях нет:** `/me` 2 запроса, ответ в тренировке 14, повторы в описи — это намеренные перечитывания под блокировкой (`FOR UPDATE`) и первая оценка дня. Число запросов резать больше некуда — дорогими оказались **отдельные запросы**.
- **Три запроса перебирали все слова курса при каждом вызове** (anti-join / join `stages → lessons → words` с повторениями ученика): «следующий урок» и прогресс курса на `/today`, карта игры. На курсе 8 тыс. слов — 3–13 мс каждый, около половины SQL-времени `/today`.
- **Планирование — ~46 % времени БД** (355 мс из 767 мс на прогон горячих эндпоинтов): запросы уходят безымянными (`DB_DISABLE_PREPARES=true`), PostgreSQL планирует каждый заново; у 4-табличных join планирование 0,3–0,4 мс при выполнении 0,01–0,5 мс.

**Сделано** (3 коммита; ответы `/today` и `/game/map` на объёме совпали со старым кодом побайтно).

### Решения координатора

**G1 — лимиты Free** (`docs/16` §3.2, `docs/04` A.2, A.16, A.17):
- **Атомарность.** Подсчёт — под `FOR NO KEY UPDATE` строки ученика, первой блокировкой транзакции (правило 16 `docs/16` §9). Две вкладки не займут последнее место дважды (PG-тест гонок). Pro блокировку не берёт.
- **Что считается.** Сессии — по `started_at` в локальном дне ученика. Вызовы на баттл — по `created_at`, равному моменту вызова. Принять баттл можно всегда.
- **Что не считается.**
  - Вызов, который не состоялся не по вине вызвавшего (отклонён, истёк, отменён, комната истекла, аннулирован), возвращается.
  - Один повтор ошибок сессии, открытой сегодня, бесплатный. Второй повтор, повтор повтора и повтор вчерашней сессии считаются как сессия.
  - Встречное приглашение (`battle_busy`) проверяется до лимита.
- **Настройка.** Пустой env — лимита этого вида нет. `0` — вид только для Pro. Каждый вид в `limits` может быть `null` отдельно.
- **Фичи entitlement читаются из конфига плана при чтении снимка.** Новая фича доходит до уже закэшированных снимков. Снимок по-прежнему пишет `features` и `new_words_per_day`: откат релиза (`deploy.sh --rollback`) или старые воркеры рядом с новым кодом читают их как раньше.

## Sprint 7.6 — VocabularyImporterTest fix ✅ (2026-04-23)

### Root cause
`tests/Unit/VocabularyImporterTest.php::sampleJson()` использовал `array_replace_recursive()` для мерджа override'ов в дефолтные данные. Для ассоциативных ключей это работает нормально, но для **нумерованных индексов массива `words`** — это делает поэлементное рекурсивное слияние ключей:

- default `words[0] = ['word' => 'hello', 'translation' => 'привет', 'part_of_speech' => 'interjection']`
- override `words[0] = ['translation' => 'только перевод']`
- результат `words[0] = ['word' => 'hello' (из default), 'translation' => 'только перевод', 'part_of_speech' => 'interjection' (из default)]`
- плюс `words[1]` остаётся целиком из default

Т.е. тест «aborts when required field is missing» фактически отправлял **валидный JSON с двумя словами** вместо одного слова без поля `word`. Поэтому `$report->aborted` был `false`, и тест падал.

### Fix
`@C:/OpenServer/domains/flash-cards/tests/Unit/VocabularyImporterTest.php:14-33` — заменил `array_replace_recursive` на простой top-level replace через `foreach`: если caller передал `'words' => [...]`, этот массив **полностью** заменяет дефолтный, а не мёржится по индексам.

Другие тесты, использующие `sampleJson(['words' => [...]])`, не сломались, потому что они либо перечисляют все нужные поля в каждом item'е, либо проверяют abort по другой причине (dup, invalid pos, size).

### Результат
Все 11 тестов `VocabularyImporterTest` зелёные. Полный прогон: **77 passed / 0 failing**.
