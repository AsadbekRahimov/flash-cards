# 21. Laravel Octane (FrankenPHP, worker mode): аудит готовности и проектное решение

> **Статус:** решение владельца 05.11.2026 — шаг 2 R13 принят; `laravel/octane` ^2.23 установлен, `config/octane.php`, `config/trustedproxy.php`, `app/Octane/*` и тесты §3.7 (1, 2, 4, 5, память) — в коде; §3.7 (3, панель и политики) — не реализован (воркер `app-api` панелей не регистрирует). php-fpm остаётся режимом по умолчанию; Octane — opt-in через `APP_SERVER=octane` в `.env`.
> **Зачем:** R12 (`PROGRESS.md`, `docs/19` §8, R12i) — 28 мс CPU на запрос под php-fpm при 3,2 мс (`/me`) и 6,2 мс (`/today`) внутри уже загруженного приложения. Разница — стоимость поднятия фреймворка на каждый запрос (линковка тысяч классов, конфиг и кэш маршрутов, регистрация двух панелей Filament, Livewire, spatie/permission, auditing, backup, Sentry, telegram-sdk, сборка контейнера и ядра). В worker-режиме это делается один раз на процесс.
> **Связанные документы:** `docs/02` §7 (деплой), `docs/07` (лимиты per IP, allowlist вебхуков), `docs/19` §4 (два Redis, circuit breaker), `docs/20` F4/A11 (scoped-память панелей), `docs/DEVOPS_GUIDE.md` §0 (php-fpm, pgbouncer).

**Где включать первым (R13, после этого аудита).** Ветка R13 разделила приложение на две поверхности (`App\Support\Surface`, docs/DEVOPS_GUIDE.md §0 «Две поверхности приложения»): контейнер `app-api` (`APP_SURFACE=api`) обслуживает только `/api/*` и не регистрирует Filament, Livewire и admin-пакеты; `app` (`full`) — панели, сайт, вебхуки. Octane поэтому включается **сначала для `app-api`** — сменой его `command:`/образа, а не для всего приложения: в этом воркере нет панелей, так что находки №12 и №17 (Filament в долгоживущем процессе) и стоимость регистрации панелей из §0 к нему не относятся, а память воркера меньше оценки §3.4 (без Filament ~50–90 МБ RSS). Переменная `APP_SERVER` из §3.2 относится к `app-api`; `app`, очереди и планировщик остаются на php-fpm до отдельного решения. Остальные выводы (TrustProxies, слушатель транзакций, `warm`, число воркеров, тесты изоляции) действуют как написано.

## 1. Модель исполнения Octane — что из неё следует для выводов

Факты проверены по исходникам `laravel/octane` 2.23.0 (`^13.0` поддерживается; `src/Worker.php`, `src/Concerns/ProvidesDefaultConfigurationOptions.php`, `config/octane.php`):

1. **Базовое приложение и sandbox.** Воркер один раз собирает приложение (`ApplicationFactory`, все провайдеры `register`+`boot`, `warm`-сервисы). На каждый запрос `Worker::handle()` делает `$sandbox = clone $this->app` (поверхностная копия: массивы `bindings`/`instances`/`resolved` копируются, объекты в них общие), ставит sandbox текущим контейнером (`app()`, фасады), отдаёт запрос ядру, затем `OperationTerminated` и sandbox выбрасывается.
2. **Что живёт между запросами:** объекты, созданные при загрузке (провайдеры `boot`, `warm`) и всё, что хранят эти общие объекты (например, репозитории внутри `CacheManager`, лимитеры внутри `RateLimiter`). Singleton, впервые разрешённый *во время* запроса, попадает в `instances` sandbox'а и умирает вместе с ним — т.е. без `warm` такой singleton пересоздаётся на каждом запросе.
3. **Что сбрасывается штатно (`RequestReceived`, по умолчанию):** sandbox конфига и URL-генератора; новый `Application` в Gate, DB, Cache, Session, Queue, Router, View, Log, Kernel; `FlushDatabaseRecordModificationState`, `FlushDatabaseQueryLog`, `FlushArrayCache` (store `array`), `FlushLogContext`, `FlushMonologState`, `FlushStrCache`, `FlushTranslatorCache`, `FlushVite`, `PrepareLivewireForNextOperation` (`Livewire::flushState()`), **`FlushLocaleState`** (локаль translator и Carbon ← `app.locale`/`app.fallback_locale` из конфига sandbox), `FlushQueuedCookies`, `FlushSessionState`, **`FlushAuthenticationState`** (guards), `EnforceRequestScheme`, новый `Request` в приложении и пагинаторе. На `OperationTerminated`: `FlushOnce`, **`FlushTemporaryContainerInstances`** (`forgetScopedInstances()` на *базовом* приложении + `octane.flush`). `DisconnectFromDatabases` и `CollectGarbage` по умолчанию выключены.
4. **Диспетчер событий не подменяется.** `events` создан при загрузке с базовым приложением; класс-слушатели и observer'ы Eloquent (`Class@method`) он разрешает через `$this->container->make()` — через **базовое** приложение, не через sandbox. Transient-зависимостям это безразлично; для `scoped` это даёт два экземпляра на один запрос (см. №12).
5. **Исключения:** `Worker::handleWorkerError()` отдаёт 500 и продолжает; воркер убивается только по `WorkerErrorOccurred → StopWorkerIfNecessary` (fatal/памяти). PDO и Redis-клиенты в конце запроса **не** освобождаются.

### 3.2 Образ, переключение режима, healthcheck

**Принцип:** одна переменная `APP_SERVER=fpm|octane` в `.env` (умолчание `fpm`, при её отсутствии всё как сегодня). Переключение — `docker compose -f docker-compose.prod.yml --env-file .env up -d app-api nginx` (Octane получает только контейнер `app-api` — TWA API; `app` с панелями и вебхуками, очереди и планировщик остаются на php-fpm).

**Dockerfile — две стадии приложения вместо одной:**
- `app-fpm` — ровно сегодняшняя стадия `app` (переименование; `nginx` берёт `public/` из неё: `COPY --from=app-fpm`).
- `app-octane` — `FROM dunglas/frankenphp:1-php8.5-alpine`; те же `apk add`, `docker-php-ext-install`, `pecl install redis`, те же проверки (`php -m`, libpq ≥ 17, OPcache ini: каталог `conf.d` в этом образе тот же `/usr/local/etc/php/conf.d/`), тот же пользователь `app`, `WORKDIR`; код и `vendor/` — `COPY --from=app-fpm /var/www/html /var/www/html` (composer один раз; PHP 8.5 в обоих образах, `composer check-platform-reqs` в сборке подтверждает набор расширений). Плюс: `cp vendor/laravel/octane/bin/frankenphp-worker.php public/` (иначе `octane:frankenphp` пишет его в `public/` при старте; файл — в `.gitignore`, в nginx-образ он попадёт, но nginx PHP-файлы не отдаёт — §3.3). `HOME`/`XDG_DATA_HOME`/`XDG_CONFIG_HOME` → каталог, доступный пользователю `app` (Caddy пишет туда); `CMD` — `docker/octane-start.sh` (shell, чтобы раскрыть переменные): `exec php artisan octane:frankenphp --host=0.0.0.0 --port=8000 --admin-host=127.0.0.1 --workers="${OCTANE_WORKERS:-6}" --max-requests="${OCTANE_MAX_REQUESTS:-500}" --log-level=WARN`. Порт 8000 наружу не публикуется. Пул `php-fpm.d` в эту стадию не копировать, `php-fpm -tt` не запускать.
- `docker/entrypoint.sh` общий (кэши `config/route/view/filament/event` до `exec "$@"` — Octane читает их при загрузке воркера так же).
- `HEALTHCHECK` в обеих стадиях — `docker/healthcheck.sh`: `fpm` → `php-fpm -t` (как сейчас); `octane` → `curl -fsS http://127.0.0.1:8000/up` (curl в образе есть; проверяет живой воркер, а не только процесс). Для compose это условие `service_healthy`, от которого зависят nginx и воркеры очередей, — не меняется.
- `stop_grace_period: 30s` у `app-api` в octane-режиме: Octane по SIGTERM дожидается текущих запросов.

**compose (`docker-compose.prod.yml`):** `app-api: build.target: app-${APP_SERVER:-fpm}`, `image: lexiflow/app-${APP_SERVER:-fpm}:${IMAGE_TAG}`; `queue-*` и `scheduler` — **всегда** `lexiflow/app-fpm:${IMAGE_TAG}` (NTS CLI, как сегодня; очереди не трогаем — `queue:work`, а не Octane). `nginx` получает `APP_SERVER` в `environment`. `deploy.sh`: `build app-fpm` всегда (его образ нужен воркерам и это путь отката), `app-octane` — когда `APP_SERVER=octane`. Откат octane → fpm: `.env` + `up -d app-api nginx`, **без сборки** (образ fpm уже есть). Включение fpm → octane — через `deploy.sh` (сборка octane-образа).

**Smoke в `deploy.sh`:** к `/up`, `/health/ready`, `/twa/index.html`, `/build/manifest.json` добавить (в обоих режимах) `POST /api/twa/auth` с пустым телом → ожидается 422/401, **не 429** (ловит схлопывание лимитов per IP при неверных прокси), и `GET /admin/login` → 200 с `https://` в ссылках на assets.

### 3.3 nginx и доверенные прокси

**nginx (`docker/nginx/prod.conf`) — как реализовано:** на Octane переезжает только `app-api`, поэтому по режиму переключается одна локация — `location ^~ /api/ { include /etc/nginx/snippets/api-${APP_SERVER}.conf; }` (`docker/nginx-entrypoint.sh` подставляет `$APP_SERVER` вместе с `$APP_DOMAIN`). Панели (`/admin`, `/org`, `/2fa`, `livewire-*`, BREACH-блок с `gzip off`), вебхуки и `location /` по-прежнему идут в `app` по FastCGI; `location ~ \.php$` остаётся для него, отдельный `return 404` для `.php` не вводился (в octane-образ `frankenphp-worker.php` копируется в `public/`, но в nginx-образ `public/` берётся из стадии `app-fpm`, а `/api/` до `\.php$` не доходит — `^~`).

- `docker/nginx/snippets/api-fpm.conf`: сегодняшнее `fastcgi_pass app-api:9000; include fastcgi_params; fastcgi_param SCRIPT_FILENAME $document_root/index.php; SCRIPT_NAME /index.php; DOCUMENT_URI /index.php; HTTPS on; fastcgi_hide_header Strict-Transport-Security; fastcgi_hide_header X-Content-Type-Options;` (`REQUEST_URI` и `QUERY_STRING` — из `fastcgi_params`, как в нынешней эмуляции внутреннего редиректа);
- `docker/nginx/snippets/api-octane.conf`: `proxy_pass http://lexiflow_api_octane;` (upstream в `prod.conf`: `server app-api:8000; keepalive 32;` — пул простаивающих соединений nginx → FrankenPHP вместо TCP-рукопожатия на каждый запрос; у php-fpm такого пула нет: он привязал бы воркер к каждому простаивающему соединению) `proxy_http_version 1.1; proxy_set_header Host $host; proxy_set_header X-Forwarded-For $remote_addr; proxy_set_header X-Forwarded-Proto https; proxy_set_header X-Forwarded-Host $host; proxy_set_header X-Forwarded-Port 443; proxy_set_header Accept-Encoding ""; proxy_set_header Connection ""; proxy_hide_header Strict-Transport-Security; proxy_hide_header X-Content-Type-Options; proxy_read_timeout 60s;`. `X-Forwarded-For $remote_addr` (а не `$proxy_add_x_forwarded_for`): клиентский заголовок отбрасывается, а не дописывается. `Accept-Encoding ""`: сжимает только nginx (BREACH-исключения для панелей сохраняются), Caddy внутри FrankenPHP ничего не сжимает, потому что не видит `Accept-Encoding`; поэтому используется **стоковый Caddyfile Octane** (`octane:frankenphp` без `--caddyfile`, `docker/octane-start.sh`), свой не поддерживаем;
- Статика (`/twa/`, `/build/`, `/storage/audio/`, `/css|js|fonts/filament`) — по-прежнему nginx (`try_files $uri`), до прокси не доходит.

**Laravel:** `config/trustedproxy.php`: `'proxies' => App\Support\TrustedProxies::fromEnv(env('TRUSTED_PROXIES'))` (CSV, пробелы и пустые элементы отброшены; `*`, `**`, `REMOTE_ADDR` и сети `/0` — `InvalidArgumentException`, т.е. `config:cache` в entrypoint роняет контейнер на старте). `Illuminate\Http\Middleware\TrustProxies` уже в глобальном списке и при пустом списке в `Middleware::trustProxies()` читает `config('trustedproxy.proxies')` на каждом запросе (Laravel 13 `TrustProxies::setTrustedProxyIpAddresses()`: `$this->proxies() ?: config('trustedproxy.proxies')`). Маску заголовков конфиг **не** задаёт: `TrustProxies::headers()` читает только статику `Middleware::trustProxies(headers:)` или умолчание класса, а умолчание включает `X-Forwarded-Prefix`, который nginx пропускает от клиента, — поэтому в `bootstrap/app.php` одна строка `$middleware->trustProxies(headers: TrustedProxies::HEADERS)` (FOR | HOST | PORT | PROTO, без PREFIX).

**Кому верить (ревью R13, 🔴1):** `TRUSTED_PROXIES` для `app-api` по умолчанию = **один закреплённый адрес nginx** (`NGINX_IPV4`, `172.28.0.10`: `networks.default.ipam.config.subnet` = `COMPOSE_SUBNET` `172.28.0.0/16`, `ip_range` = `COMPOSE_IP_RANGE`, у nginx `ipv4_address: ${NGINX_IPV4}` вне `ip_range`), **не подсеть**. Причина: соединения, которые приходят к nginx через docker-proxy (IPv6-клиенты на `[::]:443`, hairpin с хоста), nginx видит с адреса шлюза сети `172.28.0.1` — он внутри `/16`; под php-fpm `REMOTE_ADDR` = клиент, как его видит nginx, и доверие подсети позволило бы такому клиенту подделать `X-Forwarded-*`. Под Octane `REMOTE_ADDR` — всегда адрес nginx (proxy_pass), ему заголовки и принадлежат. `app`, очереди и планировщик получают **пустой** `TRUSTED_PROXIES` через якорь compose (никому не верят — как сегодня); меняется `NGINX_IPV4` → менять `TRUSTED_PROXIES` вместе с ним. `OCTANE_HTTPS=true` (`EnforceRequestScheme` — пояс к `X-Forwarded-Proto`). Тест (§3.7 (6)): `X-Forwarded-For` от недоверенного `REMOTE_ADDR` → `ip()` = `REMOTE_ADDR`; от `172.28.0.10` → заголовок; от шлюза `172.28.0.1` при одном адресе в списке → `REMOTE_ADDR`; пустой список — никому.

### 3.4 Размер: воркеры, память, таймауты, очереди

**Число воркеров (4 vCPU).** Запрос почти целиком CPU-bound, но ждёт PostgreSQL/Redis (10–20 round-trip по ~0,1–0,5 мс) и изредка TTS (№29); PostgreSQL, Redis, pgbouncer и nginx едят CPU той же машины.

`workers = round(vCPU × доля_PHP × (1 + доля_ожидания))` = 4 × 0,75 × (1 + 0,3…0,5) ≈ 4…6. **Старт — 6**, потолок без своего Caddyfile — 7 (FrankenPHP по умолчанию держит `num_threads = 2 × CPU = 8`, воркеров меньше потоков). Больше воркеров при CPU-bound нагрузке не добавляет пропускной способности, а растит p95 (контеншн ядер, очередь перед pgbouncer: `PGBOUNCER_POOL_SIZE 20` ≥ 6 воркеров + 3 очереди с запасом). Сравнение с fpm: 16 детей, из которых при насыщении большинство ждёт CPU — у Octane очередь переезжает в accept-очередь Caddy, поведение то же.

**Память.** Воркер Octane держит всё приложение резидентно (панели Filament, маршруты, Livewire, словари №1–2): ориентир 80–150 МБ RSS против 40–60 МБ у fpm-ребёнка. 6 × 150 + Caddy ~50 = ≤ 1 ГБ — укладывается в 8 ГБ рядом с PostgreSQL и двумя Redis. `OCTANE_MAX_REQUESTS=500` (умолчание Octane; перезапуск воркера ограничивает рост), `garbage: 128` (МБ; `CollectGarbage` включить), `memory_limit` PHP оставить (ini образа); наблюдать `octane:status`, `docker stats`, `memory_get_usage` в тесте §3.7 (2).

**Таймауты.** `max_execution_time: 30` в `config/octane.php` (FrankenPHP: `REQUEST_MAX_EXECUTION_TIME`) — равен нынешнему умолчанию PHP; импорт словаря/практики в Filament (≤ 2 МБ / 300 заданий) укладывается; nginx `proxy_read_timeout 60s` ≥ него. TTS-fallback — 8 с внутри.

**Очереди и планировщик** — без изменений: `queue:work`/`schedule:work` на образе `app-fpm`, свои соединения, `forgetScopedInstances` перед каждым заданием (Laravel 13). Octane на них не распространяется.

Комментарий в `config/database.php` — абзац про Octane.

- `config/permission.php`: `register_octane_reset_listener => true`.
- `config/sentry.php` — без изменений.
- `.env.example`: `APP_SERVER=fpm`, `OCTANE_WORKERS=6`, `OCTANE_MAX_REQUESTS=500`, `OCTANE_HTTPS=false`, `TRUSTED_PROXIES=` (с комментариями, какие значения в проде), `.gitignore`: `/public/frankenphp-worker.php`, `/frankenphp` (бинарник, который `octane:install` может скачать в корень вне образа), `/caddy` (данные Caddy).

### 3.7 Тесты, доказывающие изоляцию между запросами

Octane даёт тестовый harness: `Laravel\Octane\Testing\Fakes\FakeWorker` + `FakeClient` (так тестируется сам Octane: `tests/TestCase.php::createOctaneContext` — `Mockery::mock(ApplicationFactory)` возвращает **текущее** приложение теста, регистрируется `OctaneServiceProvider`, воркер `boot()`, запросы идут через настоящий `Worker::handle()` с клонированием, слушателями из `config/octane.php` и т.д.). Так тесты проверяют именно механику Octane, а не только наш `RequestHandled`-слушатель, и работают на sqlite `:memory:` теста (приложение общее).

`tests/Feature/Octane/WorkerIsolationTest.php` (Pest, без группы — идёт всегда; `tests/Support/OctaneHarness.php` — обвязка harness'а, `tests/Support/Octane/TestWorker.php` — FakeWorker без `WorkerStarting`, чьи слушатели подменяют `is_uploaded_file`/`move_uploaded_file` Symfony на весь процесс):

1. **Локаль:** ученик A (`interface_locale=uz`), ученик B (`ru`), запросы `/api/twa/me` A, B, A подряд через один воркер; ответы — на языке своего ученика (ошибка валидации `PATCH /me/settings` с невалидным значением — текст на нужном языке); после каждого запроса `app()->getLocale()` и `config('app.locale')` равны исходному `app.locale` (конфиг sandbox умер вместе с запросом); общий translator сбрасывает `FlushLocaleState` в начале **следующего** запроса — проверяется запросом без локали ученика, который видит исходную локаль.
2. **Тариф/организация:** A — Pro, участник центра X; B — Free, без центра; `/today` и `/me` подряд → `plan`, `limits`, блоки центра — свои у каждого; второй запрос B не видит снимок/entitlement A (ключи кэша по ученику — проверка, что `MeProfileCache` читает по id, а не из поля объекта).
3. **Панель и политики:** запрос страницы `/org/{slug}` владельцем (сессия через `actingAs` + cookie), затем TWA-запрос, затем `Gate::getPolicyFor(Learner::class)` внутри TWA-запроса — `App\Policies\LearnerPolicy`, не `Org…`; `Filament::getCurrentPanel()` после TWA-запроса — null; `Auth::guard('web')->user()` — null.
4. **Scoped-память (№12):** запрос владельца, в котором observer (`TelegramGroupObserver::updated` через смену `organization_id`) делает `flush()`, а до него политика уже запомнила `groups:{user}:{org}` — после сохранения в том же запросе `OrgRequestMemo::has('groups:…')` = false (с `ShareRequestMemosWithSandbox`; без него тест красный — это и фиксирует проблему); следующий запрос другого пользователя — память пуста.
5. **Транзакция (№32):** тестовый маршрут (регистрируется в тесте), который делает `DB::beginTransaction()` и бросает исключение; после запроса `DB::transactionLevel()` = 0, `report()` вызван (`Exceptions::fake()`); следующий запрос пишет в БД нормально.
6. **Прокси:** `REMOTE_ADDR` не из `TRUSTED_PROXIES` + `X-Forwarded-For: 1.2.3.4` → `ip()` = `REMOTE_ADDR`; с доверенного адреса (`172.28.0.10`, и CIDR тоже работает) → `1.2.3.4`; `X-Forwarded-Proto: https` → `isSecure()`; шлюз `172.28.0.1` при одном адресе в списке — не доверен; пустой список — никому; `X-Forwarded-Prefix` игнорируется всегда.
7. **Транзакция на входе (№32, baseline 0 вне тестов):** через воркер над тестовым приложением не смоделировать (`runningUnitTests()` там true, а откат «до 0» снёс бы транзакцию RefreshDatabase), поэтому слушатель `RememberTransactionLevels` вызывается напрямую: `RequestReceived` с Mockery-`Application` (`runningUnitTests()` → false; sandbox отдаёт `DatabaseManager` и принимает baseline) и отдельным `DatabaseManager` с одним sqlite-соединением `leak` (`:memory:`), на котором открыт `beginTransaction()`; после слушателя уровень `leak` = 0, baseline 0, `report(LeakedTransactionException)` «on entry to GET …»; второй вызов на чистом соединении ничего не репортит. Ветка отказа отката: PDO-подкласс с бросающим `rollBack()` через `DatabaseManager::extend()` → `disconnect()` (сырой PDO `null`, уровень 0), в отчёте `getPrevious()` — `PDOException`.

`tests/Feature/Octane/WorkerMemoryTest.php`: 20 учеников × (`/me`, `/today`, открыть тренировку, 3 ответа, `/finish`) = 200 запросов через воркер; `memory_get_usage()` после 50-го и после 200-го запроса — рост < 8 МБ (словари №1–2 прогреты до замера). Не бюджет Octane, а ловушка накопления в коде приложения; `PERF`-группой не помечать — должен идти в CI.

**Стенд:** `make load-test` (`tests/load/k6/twa-hot-paths.js`) в обоих режимах на одной машине и одном наборе `perf:seed`: CPU на запрос (`docker stats` app + postgres + redis), p95 по эндпоинтам, `octane:status`/RSS воркеров через 10 минут удержания; ZAP baseline повторить (заголовки идут через прокси). Числа — в `docs/19` §8 новым блоком.

**Откат:** `.env`: `APP_SERVER=fpm` → `docker compose -f docker-compose.prod.yml --env-file .env up -d app-api nginx` (образ `app-fpm` всегда собран; nginx перечитает сниппет `api-fpm.conf` из своего entrypoint). `TRUSTED_PROXIES` можно оставить — под fpm `REMOTE_ADDR` в `app-api` = клиент, адресу nginx он не равен, заголовки не учитываются; `APP_API_DB_PERSISTENT` вернуть в `true` (или убрать) — иначе fpm-контейнер работает без persistent-соединений (+20 мс на соединение, R12d). Воркеры очередей, планировщик, pgbouncer, Redis не трогаются.

### 3.9 Ожидаемый эффект

**Модель.** Сценарий k6 `twa-hot-paths.js`: 16 запросов за ≈ 31 с пауз → **0,52 запроса/с на ученика**. R12: 225 учеников × 0,52 = **117 req/s**, PHP 28 мс CPU/запрос = 3,3 ядра; PostgreSQL + Redis + pgbouncer + nginx — остаток до насыщения, ≈ 0,4–0,6 ядра, т.е. ≈ **4–5 мс CPU на запрос** вне PHP (эта доля при Octane не меняется).

**CPU PHP на запрос при Octane** = время внутри приложения (R12i: `/me` 3,2, `/today` 6,2; тренировка и хаб тяжелее) + Octane (клон, слушатели, ответ: ~0,5–1 мс) + ZTS. По составу итерации (5 просмотровых, открытие, `next`, 8 `review`, `finish`) среднее внутри приложения ≈ 10–12 мс → **≈ 11–14 мс** против 28.

| Сценарий | CPU PHP/запрос | Всего CPU/запрос (с БД, Redis) | Ёмкость 4 vCPU при бюджете 3,6 ядра | Коэффициент |
|---|---|---|---|---|
| php-fpm (R12, замерено) | 28 мс | ≈ 33 мс | 225 (факт) | 1,0 |
| Octane, пессимистично (ZTS −8 %, Octane +1,5 мс) | 15 мс | 20 мс | ≈ 350 | 1,55 |
| Octane, ожидание | 12 мс | 17 мс | ≈ 410 | 1,8 |
| Octane, оптимистично | 9 мс | 14 мс | ≈ 500 | 2,2 |

**Вывод:** на 4 vCPU — **примерно 380–470 одновременных учеников** при p95 < 300 мс (ориентир 400+), не 2,5× и не 3×: с уменьшением доли PHP ограничителем становятся PostgreSQL и Redis на той же машине; дальше масштабируют их (вынос БД, `PGBOUNCER_POOL_SIZE`, индексы). Прогноз для 8 vCPU — ~800, для 1 250 учеников — ~12 vCPU вместо ~22. p95 на лёгких эндпоинтах при малой нагрузке упадёт сильнее, чем CPU (нет 15–20 мс загрузки): `/me` и `/today` — в район 10–20 мс wall. Все цифры — до замера на стенде (§3.7); расхождение более чем в 1,3 раза от «ожидания» — повод вернуться к §3.1 (ZTS) и §3.4 (число воркеров).
