## 1. Правила

### 1.1. Сначала замер, потом правка

Медленная страница выглядит одинаково при трёх разных причинах. Их измеряют отдельно:

| Слой | Что мерить | Чем |
|---|---|---|
| Запросы | число и суммарное время SQL | query log в тесте (`DB::enableQueryLog()`), `EXPLAIN (ANALYZE, BUFFERS)` на PostgreSQL 18 |
| Рендер | время Blade и Livewire без SQL | время ответа минус время SQL |
| Payload | размер ответа Livewire | размер JSON ответа `/livewire/update` |

- **У каждой страницы списка есть тест бюджета запросов на 50 строк:** число запросов не растёт с числом строк. Это страж против N+1.
- **Замеры — на объёме** (`perf:seed`, F0), а не на демо-данных.

### 1.2. Версия Filament

Отправная точка — патч-версия с проходом производительности: v5.7.6 и новее (по статье таблицы на 50 строк с действиями быстрее примерно вдвое). У нас 5.11 — условие выполнено. Патч-обновления Filament ставим регулярно.

### 1.3. Никаких запросов в замыканиях колонок

- **Замыкания выполняются на каждую строку:** `state()`, `formatStateUsing()`, `description()`, `url()`, `color()`, `icon()`, `tooltip()`, `visible()`, `hidden()`, `disabled()`. Внутри них не обращаемся к незагруженным связям, не вызываем запросы и сервисы, которые ходят в БД.
- **Счётчики и суммы — агрегатами:**
  - на колонке: `->counts()`, `->exists()`, `->sum()`, `->avg()`;
  - в базовом запросе: `withCount()`, `withExists()`, `withSum()`.
- **`with()` — только чтобы показать поля связи, не чтобы посчитать:** он поднимает все связанные модели. В примере статьи замена на агрегаты дала 210 → 4 запроса на страницу.
- **Колонки через точку** (`learner.first_name`) Filament загружает сам. Если такая колонка ещё и в замыкании обращается к связи — проверяем, что связь уже загружена.

### 1.4. Форма запроса

- **В больших таблицах — явный `select()` нужных колонок** в `getEloquentQuery()` или `modifyQueryUsing()`. Тяжёлые `jsonb` и текстовые поля (`meta`, сырые payload провайдеров) в список не выбираем.
- **Связи загружаем с ограничением колонок:** `with(['relation:id,title'])`.

### 1.5. Индексы под настоящий запрос

- **Берём SQL, который Filament реально выполняет** (query log), и смотрим `EXPLAIN (ANALYZE, BUFFERS)` на объёме.
- **Индекс — под сортировку по умолчанию и частые фильтры.** Filament добавляет первичный ключ вторым ключом сортировки, поэтому индекс — `(колонка_сортировки, id)`.
- **`sortable()` — только на настоящих колонках.** Сортировка по аксессору не использует индекс. Для вычисляемой колонки — `sortable(query: …)` по индексируемому выражению или без сортировки.
- **Миграции индексов — с `down()`.**

### 1.6. Пагинация

- **Большие таблицы** (ориентир — от ~100 тыс. строк или там, где замер показал дорогой `COUNT(*)`):
  - `paginationMode(PaginationMode::Simple)` — без подсчёта всех строк;
  - или `PaginationMode::Cursor` — без номеров страниц, нужна стабильная сортировка.
- **Варианты «на странице»** — без `'all'`, максимум 100.

### 1.7. Поиск

- **`searchable()` — только на колонках, по которым действительно ищут.** Дорогие колонки — `searchable(isIndividual: true)`.
- **Для больших таблиц:**
  - `splitSearchTerms(false)` — один запрос, а не по запросу на каждое слово;
  - `searchDebounce('750ms')`.
- **`ILIKE '%…%'` не использует B-tree индекс.** На PostgreSQL для текстовых колонок поиска нужен `pg_trgm` с GIN-индексом. Для идентификаторов (Telegram id, id платежа) — точное совпадение через `searchable(query: …)`.
- **Глобальный поиск** включаем явно и только для ресурсов с индексированными полями.

### 1.8. deferLoading

`deferLoading()` меняет только момент, когда появляются строки, а не стоимость запроса. Включаем лишь для по-настоящему дорогих таблиц. В тестах таких таблиц перед `assertCanSeeTableRecords()` вызываем `loadTable()`.

### 1.9. Массовые действия и экспорт

- **Массовые действия на больших выборках** — `chunkSelectedRecords(250)` или задача в очереди.
- **`authorizeIndividualRecords()`** проверяет политику на каждую запись — используем осознанно.
- **Экспорт** — в очереди или потоковый CSV по частям, как `OrgActivityReportCsv`.

### 1.10. Фильтры

- **Фильтры с кнопкой «Применить»** — поведение v5 по умолчанию. На больших таблицах `deferFilters(false)` не включаем.
- **Под частые фильтры — индексы** (§1.5).
- **Фильтр Query Builder** (если появится) — с `maxRules()` и `maxNestingDepth()`.

### 1.11. Виджеты

- **Ленивая загрузка — по умолчанию,** `$isLazy = false` только у мгновенных виджетов.
- **Опрос (`$pollingInterval`)** не включаем без явной причины.
- **Тяжёлые агрегаты** — в Redis по `docs/19` §3: `Cache::flexible`, ключ с фильтрами.
- **Табличные виджеты на агрегатах** берут строки из кэшированного массива через `->records()`.

### 1.12. Деплой

- **`php artisan filament:optimize`** (кэш компонентов и Blade-иконок) — в прод-entrypoint после `view:cache`.
- **В локальной разработке не запускаем.** Сброс — `filament:optimize-clear`.
- **OPcache** — `docs/19` C7.

### 1.13. Тесты

- **Новая или изменённая страница списка** — тест бюджета запросов на 50 строк (§1.1) плюс обычные Livewire-тесты Filament.
- **Таблицы с `deferLoading()`** — `loadTable()` в тестах.

## 2. Аудит текущего кода (02.11.2026)

Объём: 116 файлов в `app/Filament`, 15 ресурсов `/admin`, 6 ресурсов `/org`, 12 виджетов админки, 2 виджета центра.

**Что уже хорошо:**
- **Связи загружаются в базовом запросе:**
  - `PracticeItemResource` — `course`, `lesson.stage`, `currentVersion`, `publishedVersion`;
  - `LearnerResource` — группы с ограничением, `withCount`, подзапросы в `select`;

- **Агрегаты:** `->counts()` используется 10 раз.
- **Ограниченные relation managers:** события ученика — с `LIMIT`, дневная статистика — окном дней.
- **Кэш виджетов:** платформенные виджеты кэшируются (`PlatformStatsService`), `SchedulerComparisonWidget` — тоже.

## 5. Чек-лист ревью Filament

Используется `reviewer` для любой фичи, которая трогает `/admin` или `/org`:

- [ ] В замыканиях колонок нет запросов и обращений к незагруженным связям; счётчики — агрегатами.
- [ ] Есть тест бюджета запросов на 50 строк для новой или изменённой страницы списка.
- [ ] Под сортировку по умолчанию и частые фильтры есть индексы (`EXPLAIN` приложен к отчёту для больших таблиц).
- [ ] Большие таблицы — простая или курсорная пагинация, явный `select()`, поиск настроен по §1.7.
- [ ] Виджеты ленивые, без опроса без причины, тяжёлые агрегаты — в кэше по `docs/19` §3.
- [ ] Массовые действия на больших выборках — частями или в очереди.
- [ ] `deferLoading()` только там, где оправдан, и тесты вызывают `loadTable()`.
