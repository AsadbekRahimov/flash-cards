## 1. Правила

### 1.1. Сначала замер, потом правка

Медленная страница выглядит одинаково при трёх разных причинах. Их измеряют отдельно:

| Слой | Что мерить | Чем |
|---|---|---|
| Запросы | число и суммарное время SQL | query log в тесте (`DB::enableQueryLog()`), `EXPLAIN (ANALYZE, BUFFERS)` на PostgreSQL 18 |
| Рендер | время Blade и Livewire без SQL | время ответа минус время SQL |
| Payload | размер ответа Livewire | размер JSON ответа `/livewire/update` |

- **У каждой страницы списка есть тест бюджета запросов на 50 строк:** число запросов не растёт с числом строк. Это страж против N+1.
- **Замеры — на объёме** (`perf:seed`, F0), а не на демо-данных.

### 1.2. Версия Filament

Отправная точка — патч-версия с проходом производительности: v5.7.6 и новее (по статье таблицы на 50 строк с действиями быстрее примерно вдвое). У нас 5.11 — условие выполнено. Патч-обновления Filament ставим регулярно.

### 1.3. Никаких запросов в замыканиях колонок

- **Замыкания выполняются на каждую строку:** `state()`, `formatStateUsing()`, `description()`, `url()`, `color()`, `icon()`, `tooltip()`, `visible()`, `hidden()`, `disabled()`. Внутри них не обращаемся к незагруженным связям, не вызываем запросы и сервисы, которые ходят в БД.
- **Счётчики и суммы — агрегатами:**
  - на колонке: `->counts()`, `->exists()`, `->sum()`, `->avg()`;
  - в базовом запросе: `withCount()`, `withExists()`, `withSum()`.
- **`with()` — только чтобы показать поля связи, не чтобы посчитать:** он поднимает все связанные модели. В примере статьи замена на агрегаты дала 210 → 4 запроса на страницу.
- **Колонки через точку** (`learner.first_name`) Filament загружает сам. Если такая колонка ещё и в замыкании обращается к связи — проверяем, что связь уже загружена.

### 1.4. Форма запроса

- **В больших таблицах — явный `select()` нужных колонок** в `getEloquentQuery()` или `modifyQueryUsing()`. Тяжёлые `jsonb` и текстовые поля (`meta`, сырые payload провайдеров) в список не выбираем.
- **Связи загружаем с ограничением колонок:** `with(['relation:id,title'])`.

### 1.5. Индексы под настоящий запрос

- **Берём SQL, который Filament реально выполняет** (query log), и смотрим `EXPLAIN (ANALYZE, BUFFERS)` на объёме.
- **Индекс — под сортировку по умолчанию и частые фильтры.** Filament добавляет первичный ключ вторым ключом сортировки, поэтому индекс — `(колонка_сортировки, id)`.
- **`sortable()` — только на настоящих колонках.** Сортировка по аксессору не использует индекс. Для вычисляемой колонки — `sortable(query: …)` по индексируемому выражению или без сортировки.
- **Миграции индексов — с `down()`.**

### 1.6. Пагинация

- **Большие таблицы** (ориентир — от ~100 тыс. строк или там, где замер показал дорогой `COUNT(*)`):
  - `paginationMode(PaginationMode::Simple)` — без подсчёта всех строк;
  - или `PaginationMode::Cursor` — без номеров страниц, нужна стабильная сортировка.
- **Варианты «на странице»** — без `'all'`, максимум 100.

### 1.7. Поиск

- **`searchable()` — только на колонках, по которым действительно ищут.** Дорогие колонки — `searchable(isIndividual: true)`.
- **Для больших таблиц:**
  - `splitSearchTerms(false)` — один запрос, а не по запросу на каждое слово;
  - `searchDebounce('750ms')`.
- **`ILIKE '%…%'` не использует B-tree индекс.** На PostgreSQL для текстовых колонок поиска нужен `pg_trgm` с GIN-индексом. Для идентификаторов (Telegram id, id платежа) — точное совпадение через `searchable(query: …)`.
- **Глобальный поиск** включаем явно и только для ресурсов с индексированными полями.

### 1.8. deferLoading

`deferLoading()` меняет только момент, когда появляются строки, а не стоимость запроса. Включаем лишь для по-настоящему дорогих таблиц. В тестах таких таблиц перед `assertCanSeeTableRecords()` вызываем `loadTable()`.

### 1.9. Массовые действия и экспорт

- **Массовые действия на больших выборках** — `chunkSelectedRecords(250)` или задача в очереди.
- **`authorizeIndividualRecords()`** проверяет политику на каждую запись — используем осознанно.
- **Экспорт** — в очереди или потоковый CSV по частям, как `OrgActivityReportCsv`.

### 1.10. Фильтры

- **Фильтры с кнопкой «Применить»** — поведение v5 по умолчанию. На больших таблицах `deferFilters(false)` не включаем.
- **Под частые фильтры — индексы** (§1.5).
- **Фильтр Query Builder** (если появится) — с `maxRules()` и `maxNestingDepth()`.

### 1.11. Виджеты

- **Ленивая загрузка — по умолчанию,** `$isLazy = false` только у мгновенных виджетов.
- **Опрос (`$pollingInterval`)** не включаем без явной причины. **Filament сам включает его на 5 с** у `StatsOverviewWidget` и `ChartWidget` (трейт `CanPoll`), поэтому у каждого такого виджета явно `protected ?string $pollingInterval = null;` (F5: `AdminDashboardCacheTest` проверяет, что `wire:poll` нет ни у одного виджета обеих панелей).
- **Тяжёлые агрегаты** — в Redis по `docs/19` §3: `Cache::flexible`, ключ с фильтрами. Образец — `Administration/Services/AdminDashboardStats` + `WidgetCache`: ключ `admin:widget:<имя>:v1:<зритель>[:<параметры>]`, зритель — `PanelDataScope::fingerprint()` (админ — `all`, учитель — его id и хэш его групп). Деньги читаются по версии данных, которую `MoneyWidgetsObserver` двигает после оплаты и возврата (`docs/19` §5.1). У таблиц-виджетов размер страницы берётся только из предлагаемых значений, а страница не дальше 1000-й.
- **Табличные виджеты на агрегатах** берут строки из кэшированного массива через `->records()`. `TableWidget` листает в простом режиме (без `COUNT`), поэтому `records()` возвращает `Illuminate\Pagination\Paginator` над `perPage + 1` строками (лишняя говорит, что страница не последняя); `LengthAwarePaginator` включил бы полный пейджер и прибавил 3–6 КБ HTML. Ключ строк — id записи (`array_column($rows, null, 'id')`), тогда `assertCanSeeTableRecords([$model])` работает как раньше.

### 1.12. Деплой

- **`php artisan filament:optimize`** (кэш компонентов и Blade-иконок) — в прод-entrypoint после `view:cache`.
- **В локальной разработке не запускаем.** Сброс — `filament:optimize-clear`.
- **OPcache** — `docs/19` C7.

### 1.13. Тесты

- **Новая или изменённая страница списка** — тест бюджета запросов на 50 строк (§1.1) плюс обычные Livewire-тесты Filament.
  - **Помощник:** `Tests\Support\FilamentQueryBudget::assert(ListX::class, $fill, ceiling: N)`. Он рисует страницу на 10 и на 50 строках, требует одинаковое число запросов, не больше `ceiling`, и при провале называет запрос, который повторяется на каждую строку.
  - **`$fill(int $rows)`** доводит таблицу ровно до `$rows` записей — с теми связанными строками, которые читают колонки (группа, подписка, участие в центре): на голых строках N+1 не виден.
  - **Примеры:** `tests/Feature/Filament/ListQueryBudgetTest.php` — ученики `/admin` и участники центра `/org` (с входом в панель и арендатором). Для известного, ещё не исправленного N+1 есть параметр `knownPerRow`; исправление (F4) возвращает его к 0.
- **Таблицы с `deferLoading()`** — `loadTable()` в тестах.

- **Роль teacher — сделано (W2-A, второй заход).** Было: `LearnerPolicy::view` и `ExamSessionPolicy::view` спрашивали базу по 6 раз на строку списков учеников и экзаменов (ссылка строки, кнопка просмотра, действия) — 306 и 310 запросов на 50 строк. Итог: 306 → 10 и 310 → 12 запросов на 50 строк (два запроса в окне замера, по 5–6 на запрос), `knownPerRow: 0`; изоляция (учитель A не видит учеников и экзамены B — в списке, по URL, через Gate) — `TeacherRowPolicyTest`.
- **`sortable()` на агрегатах — сделано (W2-A, второй заход):** у `referrals_count` учеников (200 тыс.) сортировка снята (`AdminTableSettingsTest`); `results_count` и `answers_count` экзаменов (10 тыс. строк) остаются сортируемыми.
- **Размеры страницы в `/org` — сделано (W2-A, второй заход):** все пять списков кабинета и relation manager результатов задания — `AdminTable::bounded` (10/25/50/100, `enforcePaginationPageOptions()`): подделанный `tableRecordsPerPage` (`all`, миллион) получает 10 строк, а не всех участников центра (`OrgTableSettingsTest`).

**Что показал `EXPLAIN` (W2-A):**
- **Сортировка по имени и поиск по имени спорят за план.** Поиск Filament — `lower(col) like '%…%'` плюс `username ilike` в одном `OR`; GIN-триграммы дают BitmapOr, и `count(*)` поиска падает с 80 до 16 мс. Но у страницы с `order by first_name, id limit 10` планировщик при «частом» термине (≥ ~0,5 % строк по оценке) выбирает обход `learners_first_name_id_idx` с фильтром, рассчитывая на равномерное распределение совпадений, — а совпадения по имени лежат в одном месте алфавита. Поиск «aziz» обходит 25 000 строк (135–256 мс), «zilola» — 195 000 (430–790 мс при нагрузке); без индекса было 94 мс (seq scan + sort), bitmap-план — 43 мс. **Рекомендация для F3:** `LearnerResource` — сортировка по умолчанию `id desc` (новые первыми; `defaultSort('id', 'desc')`): страница по умолчанию 0,1 мс по первичному ключу, поиск частого имени 0,4 мс (обход PK назад, совпадения равномерны), редкого — bitmap + sort 4,6 мс; `learners_first_name_id_idx` остаётся под сортировку по имени по клику. Форма индексов и форма запроса должны совпадать: если F3 переведёт поиск имени на `whereLike` (`ilike` по колонке), индексы `lower(first_name)` / `lower(last_name)` надо заменить на обычные `gin (first_name gin_trgm_ops)`.
- **Редкий короткий термин при сортировке по `id` — худший случай поиска, принят (решение координатора по ревью W2).** Планировщик оценивает совпадения трёх-четырёх буквенного термина по триграммам с запасом и при `order by id … limit 10` предпочитает обход первичного ключа с фильтром, рассчитывая найти десять строк быстро; когда совпадений мало или нет, обход идёт по всей таблице: на 200 тыс. учеников «olim» — 162 мс, «qqq» — 324 мс; у слов «kari» — 17–104 мс, «qqq» — 80 мс. Принудительный seq scan с сортировкой для таких терминов был бы быстрее (замер повторного ревью: «olim» — 61–66 мс против 175–211 мс обхода PK, у слов «qqq» — 20 мс против 28–38 мс), но планировщик сам его не выберет, а подсказок планировщику PostgreSQL нет. Это только админка и только редкие термины; частые и обычные (имя, фамилия, username, слово) — bitmap-план за единицы миллисекунд. Ограждение поиска подзапросом (сначала `whereIn` по bitmap, затем сортировка) отвергнуто: оно удорожает частый поиск, который и есть основной случай.
- **Сортировки по клику `last_seen_at` / `created_at` у учеников** — 265–275 мс (seq scan + top-N; одиночный индекс `last_seen_at` не покрывает `order by last_seen_at desc, id desc`). Если они нужны админам часто — `(last_seen_at, id)` вместо `last_seen_at` и `(created_at, id)` (F3 решает по использованию).
- **Виджеты дашборда `/admin` индексами не лечатся — нужны другие запросы (F5, вместе с кэшем `docs/19` C3).** **Сделано (W2-C, F5, 02.11.2026):** все пять переписаны так, как описано ниже, и стоят под кэшем; результат сравнён с прежним запросом тестом `AdminDashboardQueriesTest` (админ и учитель), цифры — выше, «Что показал замер «после» (F5)»; partial-индекс `learners_deleted_idx` добавлен вместе с запросом мест центров (`docs/03` §2.17):
  - `HardestWordsTableWidget` — 2 557 мс: Seq Scan по 100 000 слов с тремя коррелированными подзапросами по `training_reviews` на каждое слово (3,9 млн buffers). Один агрегат по `training_reviews` за 30 дней — `select word_id, count(*), sum(quality < 3)::float / count(*) … group by word_id having count(*) >= 5 order by 3 desc limit 10` — и `joinSub` к `words`; для админа не добавлять `whereIn(training_session_id)` (все сессии — пустой фильтр с hash join по 60 000 id).
  - `TopLearnersTableWidget` — 1 271 мс: hash join 200 000 учеников с агрегатом + коррелированный `withCount` на каждого из 60 000 кандидатов (1,45 млн buffers). Тот же приём: агрегат `group by learner_id order by count(*) desc limit 10`, затем `whereIn` 10 учеников с группами.
  - `ActivityChartWidget` — 249 мс: Seq Scan 600 000 отзывов + hash join со всеми сессиями (пустой фильтр админа) + HashAggregate по дате. Для админа — без `whereIn`; на годовой истории индекс `(created_at, learner_id)` даст range scan; результат — в кэш.
  - `TotalLearnersWidget` — 19 + 28 мс (bitmap по `last_seen_at` и `count(*)` таблицы) — только кэш.
  - `OrganizationSeatsTableWidget` — 74 мс: подзапрос на каждую из 100 организаций с join `learners` по первичному ключу ради `deleted_at is null` (32 000 поисков, 128 000 buffers). Заменить join на анти-join по удалённым — `whereNotExists(learners where id = om.learner_id and deleted_at is not null)` — с partial-индексом `learners (id) WHERE deleted_at IS NOT NULL` (удалённых единицы; индекс добавлять вместе с этим запросом).

## 5. Чек-лист ревью Filament

Используется `reviewer` для любой фичи, которая трогает `/admin` или `/org`:

- [ ] В замыканиях колонок нет запросов и обращений к незагруженным связям; счётчики — агрегатами.
- [ ] Есть тест бюджета запросов на 50 строк для новой или изменённой страницы списка.
- [ ] Под сортировку по умолчанию и частые фильтры есть индексы (`EXPLAIN` приложен к отчёту для больших таблиц).
- [ ] Большие таблицы — простая или курсорная пагинация, явный `select()`, поиск настроен по §1.7.
- [ ] Виджеты ленивые, без опроса без причины, тяжёлые агрегаты — в кэше по `docs/19` §3.
- [ ] Массовые действия на больших выборках — частями или в очереди.
- [ ] `deferLoading()` только там, где оправдан, и тесты вызывают `loadTable()`.
