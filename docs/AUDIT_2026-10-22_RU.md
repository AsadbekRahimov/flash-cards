# Аудит LexiFlow Pro — 22 октября 2026

Проверяемая версия: `55ce5b7`. Исходное рабочее дерево было чистым. Проверка выполнена по запросу владельца: соответствие описанию, код, бизнес-логика, безопасность и рекомендации. Исправления прикладного кода не вносились.

## Вывод

Проект имеет развитую основу: доменные сервисы, API Resources, политики доступа, транзакции и ограничения БД, тесты конкуренции, отдельный кабинет организации, версионирование JWT и поддержка нескольких языков. Однако готовность к эксплуатации нельзя определять по количеству реализованных функций. Найдены дефекты в основном Telegram-сценарии и контроле доступа. Их следует исправить до запуска новых центров и включения продаж.

Отчёт разделяет воспроизведённые дефекты, выводы по коду, ограничения проектирования и задачи ручной приёмки. Это широкий инженерный аудит репозитория, а не доказательство отсутствия любых иных ошибок. Реальная инфраструктура, устройства пользователей и платёжные кабинеты не были доступны для проверки.

## 2. Ошибки высокого приоритета — P1

### F01. Кнопки групповых тренировок и экзаменов используют недопустимый для группы web_app

**Доказательство:** `app/Domain/Telegram/Services/TelegramKeyboardFactory.php:12–18` всегда создаёт `inline_keyboard` с полем `web_app`. `IrazasyedTelegramClient::sendWebAppButton` передаёт его в sendMessage без учёта типа чата. StartTrainingHandler, StartTrainingCallbackHandler и StartExamHandler вызывают этот метод с идентификатором группового чата.

**Что ломается:** центральная история продукта: учитель запускает занятие в группе и ученики получают кнопку открытия приложения. Согласно актуальному Bot API поле InlineKeyboardButton.web_app доступно только в личном чате пользователя с ботом. Код создаёт серверную сессию до попытки отправить кнопку; после отказа Telegram сессия остаётся открытой. Для экзамена повтор команды встречает already_open.

**Уверенность:** подтверждено путём исполнения и официальным контрактом; живой запрос в Telegram не выполнялся.

**Исправление:** разделить кнопки для личного и группового чата. Для группы использовать обычную URL-кнопку с Telegram Mini App direct link, а контекст занятия передавать через startapp. Во фронтенде обработать start_param/tgWebAppStartParam и открыть нужную тренировку/экзамен. Для личных напоминаний web_app можно сохранить. Обычная ссылка на HTTPS SPA сама по себе не заменяет Mini App launch с авторизационным контекстом.

**Проверка:** контрактные тесты должны проверять настоящий reply_markup, а не только вызов мок-метода sendWebAppButton. Затем ручной сценарий с реальным ботом в supergroup.

Источники: [InlineKeyboardButton](https://core.telegram.org/bots/api#inlinekeyboardbutton), [Direct Link Mini Apps](https://core.telegram.org/bots/webapps#direct-link-mini-apps).

### F02. Неактивный учитель продолжает управлять обучением через бота

**Доказательство:** `TrainingSessionService::userTeachesGroup` (строка 496) и `ExamSessionService::userTeachesGroup` (строка 185) проверяют только наличие teacher_groups. Входящие handlers находят User по telegram_user_id без фильтра is_active. CloseExamHandler также проверяет только teacher_groups. Для сравнения StatsCommandHandler уже фильтрует активных пользователей.

**Воспроизведение:** создан User с `is_active=false`, активная группа и сохранённая связь teacher_groups; затем вызваны оба сервиса открытия сессии. И тренировка, и экзамен получили status=open. Временный Pest-сценарий прошёл именно с этим нежелательным результатом.

**Последствие:** блокировка аккаунта администратором не отзывает полномочия Telegram-команд. Сохранившаяся связь с группой позволяет запускать занятия и закрывать экзамены.

**Исправление:** единое правило авторизации преподавательских действий: активный пользователь + разрешённая связь с группой + допустимый статус группы. Применить в сервисах, командах и callbacks. Не ограничиваться скрытием кнопок или блокировкой входа в Filament. Роли кабинета центра учитывать отдельно от платформенных Spatie roles.

**Проверка:** тесты блокировки/разблокировки учителя для start_training, picker callback, start_exam и close_exam.

### F03. 2FA админки принимает отметку другого аккаунта

**Доказательство:** `RequireTwoFactor.php:28` проверяет только наличие `2fa.passed_at`. `TwoFactorController::markPassed` записывает и время, и `2fa.user_id`, но middleware админки второй ключ игнорирует. В `RequireOrgTwoFactor.php:42` привязка к user_id уже реализована.

**Воспроизведение:** изолированный вызов middleware с активным по условию admin mock, включённой 2FA и сессией, содержащей произвольный чужой user_id, пропускает запрос: `ADMIN_ALLOWED`.

**Последствие:** при одновременной авторизации разных аккаунтов через web/org guards в общей браузерной сессии отметка прохождения 2FA одного пользователя может удовлетворить проверку админки другого. Это обход второго фактора при определённом состоянии сессии; не вход без пароля.

**Исправление:** сверять user_id на обеих панелях; хранить контекст подтверждения по guard/аккаунту; сбрасывать отметки при смене пользователя. Setup pending_secret и разрешение показа recovery codes тоже следует привязать к аккаунту.

**Проверка:** два разных пользователя одновременно в web/org, прохождение 2FA одним из них не открывает доступ второму.

### F04. Нет ограничения попыток проверки 2FA

**Доказательство:** группа маршрутов `routes/web.php:74` содержит только web и auth:web,org. POST setup и POST challenge не имеют throttle. В TwoFactorController::confirm/verify нет RateLimiter. В Nginx-конфигурации соответствующего ограничения тоже не найдено. Дополнительный Pest-сценарий проверил отсутствие throttle у маршрута 2fa.verify.

**Последствие:** после получения первого фактора атакующий может многократно пробовать коды TOTP и recovery codes. CSRF и ограничение попыток на странице логина это не заменяют.

**Исправление:** лимиты по аккаунту и IP для confirm/verify, временная задержка после серии неудач, аудит подозрительных попыток. Для TOTP дополнительно запретить повторное использование уже принятого временного шага. Recovery codes уже потребляются атомарно — эту защиту сохранить.

**Проверка:** серия ошибочных кодов даёт 429, лимиты независимы для разных аккаунтов, восстановление после cooldown работает.

## 3. Замечания среднего приоритета — P2

### F05. CI проверяет одну ревизию, а production может получить другую

В `.github/workflows/ci.yml` выполняются тесты и Docker build текущего коммита, затем SSH вызывает deploy.sh. Но `deploy.sh:18` делает `git pull --ff-only`, а далее заново собирает образы на сервере.

Если после запуска CI в ветку попал новый коммит, deploy может взять его до завершения его проверок. Также повторная сборка с плавающими базовыми образами не гарантирует тот же результат.

Рекомендация: собирать и публиковать image с тегом commit SHA, разворачивать проверенный digest. Как минимум передавать точный SHA и проверять его перед сборкой. Добавить serialization/concurrency для production deploy, чтобы два workflow не запускали миграции и переключение одновременно.

### F06. Подтверждение 2FA может проверять не тот guard

Общие маршруты используют `auth:web,org`, а контроллер берёт Auth::user(). При двух залогиненных аккаунтах приоритет имеет web. Переход из org-панели сам по себе не передаёт проверяемый guard.

Следствие по коду: владелец центра, вошедший в org как B и одновременно в admin как A, может попасть на проверку кода A. Это отдельная проблема выбора аккаунта; F03 относится к принятию уже существующей отметки.

Рекомендация: отдельные маршруты/контроллерный контекст для панелей либо серверный, привязанный к сессии challenge с user_id и guard. Сквозное воспроизведение в браузере в рамках аудита не выполнялось.

### F07. У инструментов TWA есть известные уязвимые зависимости

npm audit по полному дереву показал 17 затронутых пакетов, включая happy-dom и vitest с critical. Это количество пакетов в audit, а не 17 независимых эксплуатируемых ошибок сайта. Runtime-проверка --omit=dev для root/TWA вернула 0.

Риск относится прежде всего к машине разработчика, тестовым серверам и CI при работе с недоверенным кодом. Например, advisory happy-dom описывает выход из VM при выполнении недоверенного JavaScript; advisory Vitest — чтение/исполнение файлов при соответствующих условиях запуска UI/API сервера. Наличие записи audit не означает, что production SPA можно эксплуатировать этим способом.

CI сейчас проверяет npm только с --omit=dev и такие проблемы пропускает. Нужны отдельный audit dev-инструментов, совместимое обновление Vite/Vitest/happy-dom и полный повтор тестов/сборок. Не выполнять npm audit fix --force вслепую: предлагаются и major upgrades.

Источники: [Happy DOM advisory](https://github.com/capricorn86/happy-dom/security/advisories/GHSA-37j7-fg3j-429f), [Vitest advisory](https://github.com/vitest-dev/vitest/security/advisories/GHSA-5xrq-8626-4rwp). Машиночитаемый результат: storage/logs/audit-npm-twa.json.

### F08. Время выполнения задания вычисляется приблизительно, хотя показывается как факт

`AssignmentService::completionMoment` (строка 568) использует последние даты повторений WordRepetition. Но модель хранит последнее повторение, а требования docs/13 §1.4 говорят о первом достижении порога и различении сдачи до/после дедлайна.

Пример: ученик выполнил порог до дедлайна, затем повторил слова после него; снимок ещё не успели пересчитать. Последние даты уже после дедлайна, и отчёт способен показать опоздание. Ограничение честно описано в комментарии к методу, но не устраняет смысловую ошибку результата для учителя.

Рекомендация: фиксировать достижение порога по событиям принятых оценок либо восстанавливать первый момент по training_reviews. Текущий дешёвый snapshot оставить для прогресса; точную дату хранить отдельно. До изменения интерфейс должен обозначать оценочный характер времени.

## 4. Известные эксплуатационные риски и улучшения

Эти пункты не объявлены доказанными production-инцидентами.

1. **Демо-аккаунты.** DatabaseSeeder всегда вызывает DemoAdminSeeder и остальных demo seeders. DemoAdminSeeder создаёт/обновляет admin@local с известным паролем. Production-гайд уже запрещает общий db:seed, что правильно. Добавить машинную защиту в demo seeders: разрешать только local/testing либо требовать явный demo-mode. Одна инструкция в документации не предотвращает ошибочный запуск --force. При новой demo-записи атакующий мог бы сам пройти первоначальную настройку 2FA.
2. **Deploy smoke слишком узкий.** deploy.sh проверяет /up и artisan about; это не проверяет работу очереди и scheduler. После времени на прогрев проверять /health/ready и основные публичные/TWA assets. Нужен понятный rollback на предыдущий image; миграции должны быть совместимы с предыдущей версией приложения либо иметь отдельный план восстановления.
3. **Один worker на все очереди.** Production queue:work слушает high,default,low одним процессом. Длительная задача занимает его целиком; непрерывная high-нагрузка отодвигает остальные. Выделить worker для high и worker для фоновых задач, измерить задержку выполнения. Не добавлять тяжёлую систему управления очередями без необходимости.
4. **Readiness очереди.** Проверка размера backlog полезна, но маленькая очередь не доказывает, что worker работает. Дополнить heartbeat/возрастом самой старой готовой задачи и проверкой low. Scheduler heartbeat уже существует.
5. **Конкурентное построение результатов экзамена.** LeaderboardBuilder::build удаляет и создаёт exam_results в транзакции без собственного session lock. Его вызывают разные пути: закрытие экзамена, result API, job. Потенциальна гонка двух первых построений. Нужен PostgreSQL concurrency-тест для одновременного result/job/close; при подтверждении — общая блокировка строки сессии и единая точка финализации. Гонка здесь не воспроизводилась.
6. **Потерянные побочные действия.** Изменение статуса и последующая постановка уведомления в очередь местами разнесены. Например, ChallengeService::close сначала сохраняет finished, затем ставит DMs; сбой между этими шагами теряет уведомление. Для денежных действий и важных уведомлений разумны outbox/recovery-механизмы. Referral recovery уже показывает подходящий паттерн.
7. **Обновление JWT при параллельных 401.** API client вызывает auth.login отдельно для каждого запроса. После истечения токена несколько параллельных загрузок могут одновременно обращаться к /auth. Добавить общий Promise для одного выполняющегося refresh; при неуспехе очищать старый токен. Проверить поведение после длительного простоя и при потере сети.
8. **Смысл Revenue last 30 days.** BillingReportService фильтрует исходные charges по occurred_at и вычитает возвраты именно этих charges. Возврат сегодня за покупку старше 30 дней не попадёт в показатель. Это корректный когортный показатель, но не денежный поток за период. Разделить и ясно назвать gross charges in period, refunds in period, net cash movement. Не складывать UZS и XTR; текущий код уже разделяет валюты.
9. **Размер крупных сервисов.** SubscriptionService, PaymentApplier, OrganizationMembershipService, AssignmentService и Engagement-сервисы несут много сценариев. После исправления багов выделять отдельные операции/политики и переходы состояний, сохраняя транзакционные границы. Переход на микросервисы сейчас увеличит сложность согласованности.
10. **Защита статической TWA.** SPA отдаёт Nginx, поэтому Laravel SecurityHeaders для её index.html не выполняется. Проверить и задать нужные CSP, nosniff, Referrer-Policy непосредственно в Nginx с учётом Telegram Web и источников аудио. Не копировать frame-ancestors self без проверки: это может блокировать встраивание Telegram Web.

| Продакшен-приёмка | В PROGRESS и staging checklist она явно оставлена открытой |

Рекомендации по самому продукту:

- Сделать устойчивым путь: учитель подключает группу → назначает урок → ученик открывает TWA → получает первый результат → учитель видит прогресс. Ошибка в этом пути важнее новой игровой механики.
- Объяснять ученику разницу между «повторил», «правильно ответил» и «выучил». Самооценка карточки не равна независимой проверке знания; это особенно важно для рейтингов и отчётов центров.
- Лиги/вызовы на количестве повторений допускают мотивацию к быстрым низкокачественным действиям. Рассмотреть ограничения повторного начисления за одно слово и отдельные режимы честного соревнования. Не менять XP без согласованного продуктового правила.
- Симулятор текущей реализации — vocabulary mock, а не полноценная оценка IELTS/SAT. Процентиль считается по попыткам, включая собственную; несколько попыток одного человека влияют на распределение. В интерфейсе пояснить базу сравнения и не выдавать показатель за официальный экзаменационный балл.
- Для учителя полезнее видеть конкретные трудные слова и учащихся, которым нужна помощь, чем только общий рейтинг.
- Для платного тарифа показывать источник доступа: личная подписка или место центра, дату окончания и последствия выхода из центра. В коде это уже сложная составная модель, её стоит объяснять простыми текстами.

## 6. Документация и сопровождение

Документы накоплены из нескольких фаз. В docs/08 roadmap остаются незакрытые ранние пункты, students, PHP 8.2 и альтернативный bot SDK, тогда как composer требует PHP 8.3, реализован learner-first и используется irazasyed adapter. docs/02 также содержит устаревшие ADR/открытые вопросы рядом с актуальными решениями о tenancy.

Нужно явно обозначить порядок актуальности: текущая модель/контракт → принятые уточнения Фазы 2 → исторический roadmap. Перенести старые формулировки в историю, а не оставлять рядом как действующие требования. В PROGRESS разделять «код готов», «автотесты прошли», «ручная приёмка пройдена», «разрешён production».

Окружение разработчика также требует стандартизации:

- vendor должен совпадать с composer.lock; исходное несоответствие затрагивало не только Sentry, но и версии Filament и других библиотек;
- PHP timezone тестового процесса фиксировать UTC до загрузки файлов Pest: часть тестовых дат создаётся раньше Laravel bootstrap;
- Composer сообщал, что SSL/TLS protection disabled. Это настройка текущей машины/инструмента, а не доказанная настройка репозитория. Восстановить проверку TLS и корректный CA bundle; после этого повторить проверку зависимостей по защищённому каналу. Значения глобальной конфигурации в аудите не менялись;
- проверять PostgreSQL и Redis отдельным интеграционным прогоном. SQLite не проверяет реальные row locks и часть PostgreSQL constraints;
- для PHP/Node версий иметь единый документированный минимум и воспроизводимый контейнер.
