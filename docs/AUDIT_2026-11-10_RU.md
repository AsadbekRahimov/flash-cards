## 1. Безопасность

### Высокий

**H1. Сотрудник центра может присвоить любой Telegram ID без подтверждения.** 📋
`app/Filament/Org/Pages/OrgProfile.php:24-32` — поле `telegram_user_id` вводится руками, проверка только `unique`. Ему доверяют
`OrgGroupLinkService.php:44-64`, `DmLearnerResolver.php:34`, `StartCommandHandler.php:85`.
- *Угон группы между центрами:* владелец центра вписывает ID человека, который админ в чужой, ещё не привязанной группе с ботом,
  и привязывает её по `chat_id` — проверка `getChatMember(chat, заявленный_id)` проходит. Он видит учеников и активность чужого класса.
- *Блокировка ученика:* любой сотрудник вписывает ID произвольного ученика — бот начинает считать того учителем и перестаёт отвечать ему как ученику.
- *Как чинить:* убрать поле. Привязка через бота: в `/org/profile` одноразовый код → `t.me/<bot>?start=link_<код>` → сервер сохраняет
  `message.from.id`. Существующие значения перепроверить. Это же решение снимает главную UX-проблему кабинета (§4 P1).

### Средний

**M1. Host не закреплён — можно отравить ссылку сброса пароля (VPS-деплой).** ✅
Нет `trustHosts()`, `docker/nginx/prod.conf` отвечает на любой Host. Атакующий отправляет форму сброса `/org` для чужого e-mail с
`Host: evil.com` — жертве приходит настоящее письмо со ссылкой на `evil.com` с токеном. Режим `CLOUDFLARE_ONLY` не спасает.
Исправление: `trustHosts` по `APP_URL` (+ `APP_TRUSTED_HOSTS`), catch-all `default_server` в nginx.

**M2. Владелец центра может зачислить любого ученика платформы без его согласия.** 📋
`MemberResource.php:138-148,240-260`, `OrganizationMembershipService.php:162`. Вводится `@username` или ID — членство активно сразу,
владелец видит имя, серию, активность; ответ `learner_not_found` раскрывает, кто пользуется платформой. В docs/13 это описано как
задуманное, но ссылки-приглашения спрашивают согласие, а этот путь — нет. Предложение: приглашение, которое ученик подтверждает в боте.

**M3. Coolify: php-fpm и Octane доступны всем контейнерам общей сети.** 📋
`docker-compose.coolify.yml`: скомпрометированное соседнее приложение может говорить FastCGI с `lf-app:9000` (исполнение кода) и
слать в `lf-api:8000` поддельный `X-Forwarded-For`. Нужно: `lf-app`/`lf-api`/`lf-nginx` в приватной сети стека, к сети прокси — только nginx,
`TRUSTED_PROXIES` — адрес nginx. Не делалось без возможности проверить деплой.

**M4. Coolify: корректность IP клиента зависит от настроек Traefik вне репозитория.** 📋 (не подтверждено)
Проверка: ~70 запросов `/api/twa/auth` с меняющимся `X-Forwarded-For` — должен прийти 429.

### Что делать для роста RPS, по порядку

1. Выставить на сервере `SENTRY_TRACES_SAMPLE_RATE=0` (или ≤0.01) и выключить breadcrumbs SQL/cache для API.
2. Прогнать k6 со ступенями `OCTANE_WORKERS` 4 → 6 → 8, следя за простоем CPU и `cl_waiting` в pgbouncer; поднять `API_MEM_LIMIT`.
3. Дописать в k6 сценарии со зрелыми карточками, игрой, практикой и баттлом — сейчас измеряется только самый лёгкий путь.
4. Решить про `synchronous_commit=off` (для учебных карточек потеря долей секунды данных при аварии обычно приемлема).
5. Вынести раздачу аудио на nginx (`X-Accel-Redirect`), объединить `/today` и `/assignments`.

Уже сделано хорошо и трогать не нужно: нет session/cookie-middleware на API, лимитер одним Lua-скриптом, версионированные кэши,
индексы под горячие запросы (недостающих составных не найдено), pgbouncer в transaction mode, ленивые маршруты и immutable-ассеты клиента.
