# k6: нагрузочные сценарии LexiFlow

Запускаются на **staging** (не на проде: `load:tokens` и сид отказываются работать при `APP_ENV=production`), из образа
`grafana/k6` через `make`; ничего не ставится. Общий порядок и пороги приёмки — `docs/STAGING_PHASE2_CHECKLIST.md` §7.3.

| Файл | Что нагружает | Команда |
|---|---|---|
| `twa-hot-paths.js` | Главная, профиль, курсы, каталог, тренировка **со свежими** карточками (все flash) | `make load-test` |
| `twa-training-mature.js` | тренировка со **зрелыми** карточками: meaning / reverse / audio (варианты с дистракторами строит сервер; ответ — один из вариантов), у Pro — ввод (spelling / gap-fill) | `make load-test-mature` |
| `game-caravan.js` | игра «Караван»: карта, старт забега, ответы до конца, итог | `make load-test-game` |
| `practice-session.js` | практика: сессия одного режима (`PRACTICE_MODE`) от хаба до последнего ответа | `make load-test-practice` |
| `battle.js` | баттл: пара учеников от приглашения до результата, опрос 5 с / 3 с / 2 с | `make load-test-battle` |
| `mixed-profile.js` | всё вместе в долях по оценке аудита (просмотр — пятым потоком, `MIX_BROWSE`) | `make load-test-mixed` |
| `arrival-burst.js` | **всплеск открытий** Mini App после рассылки или объявления в группе класса: заданный темп поступления (`ramping-arrival-rate`) | `make load-test-burst` |
| `telegram-webhook.js` | вебхук Telegram | `make load-test-webhook` |
| `flows.js`, `lib.js` | общие функции (не запускаются); в `flows.js` — потоки, в том числе `browse()` / `openToday()` (просмотр главной и каталога) | |
| `plan.js`, `plan.test.js` | чистая арифметика без импортов k6: распределение смеси, диапазоны токенов, срок токенов, выбор токенов всплеска; тесты на Node | `make load-plan-test` |

## Подготовка (один раз на стенд, повторять по мере надобности)

```bash
make load-tokens TARGET_VUS=1250      # тестовые ученики Load1..LoadN и их JWT (срок TOKENS_TTL, умолчание 7200 с) -> tests/load/k6/tokens.json (0600)
make load-seed                        # зрелые карточки + пилот практики + пары друзей (1-2, 3-4, ...)
```

`make load-seed` = `php artisan db:seed --class=LoadScenarioSeeder --force` (`database/seeders/LoadScenarioSeeder.php`), работает
только с учениками с меткой `meta.load_test` (их создаёт `load:tokens`), в окружениях `local | testing | staging`:

- каждому — строки `word_repetitions` для первых `LOAD_SCENARIO_WORDS` (умолчание 300) активных слов курса: состояние `review`,
  `repetitions` циклом 2..7, **срок наступил**. Так селектор упражнений отдаёт flash / reverse / audio, на каждом третьем проходе
  (3, 6) — ввод (только у Pro: `exercise.spelling` / `exercise.gap_fill`; у Free эти карточки заменяются на rotate). Это же даёт доступ
  к практике / игре / баттлу — задание выдаётся ученику, «знакомому» со всеми его словами;
- `practice_pilot_at` (для стенда с `PRACTICE_ACCESS=pilot` / `GAME_ACCESS=pilot`);
- дружба внутри пар (1-2, 3-4, ...) через `FriendshipService`.

Повторный запуск идемпотентен и **снова делает карточки «наступившими»** — так «перезаряжают» учеников после долгого прогона
(иначе дневной обзор кончится: `training_review_coverage` < 0.9). `LOAD_SCENARIO_COURSE=<slug>` — другой курс. Чтобы у ученика была
карточка ввода, ему нужен Pro (выдать через админку / подписку); без Pro сценарий всё равно проходит путь с дистракторами.

Настройки стенда (`.env` staging), без которых сценарии упираются в лимиты Free и это видно в `flow_aborted`:

```dotenv
PRACTICE_ACCESS=all
PRACTICE_FREE_SESSIONS_PER_DAY=        # пусто = без лимита для Free (умолчание 2 в день)
PRACTICE_FREE_BATTLES_PER_DAY=         # умолчание 1 в день
GAME_ACCESS=all
GAME_FREE_RUNS_PER_DAY=                # умолчание 1 в день
```

Нужен опубликованный контент практики (`php artisan practice:import <файл> --publish`) и, для диктанта, его аудио.

## Как отвечают скрипты

API **не отдаёт правильные ответы** (docs/16 §12), а k6 не ходит в БД стенда (браузерный e2e `resources/twa/scripts/e2e` читает снимок
сессии из SQLite — удалённому стенду такое недоступно). Поэтому ученик в k6 **угадывает**: `answerFor()` в `lib.js` строит ответ по
тому, что показывает API (`options` → случайный `option_id`, `fragments` → перемешанный `order`, пары → `left_id`/`right_id`,
ввод → `test`). Сервер делает ту же работу для неверного ответа, что и для верного (оценка, снимок, состояние, счётчики) — это и
измеряется. Следствие: забег «Каравана» у угадывающего часто кончается, когда фляги вышли, а не на последнем элементе; оба конца
считаются завершением (`flow_completed`).

## Метрики и пороги

Общие: `server_errors` (любой 5xx — провал), `rate_limited` (429 — провал: сценарий быстрее лимитеров, а не сервер медленный),
`checks > 99 %`, `http_req_failed < 1 %`, `flow_completed > 95 %` (прогон дошёл до естественного конца: сессия закрыта, забег окончен,
матч закрыт), `flow_aborted` (с тегами `step` — где остановился: `training_mature`, `game_run`, `practice_answer`, `battle`, … — и
`status`: отказ API — лимит, нет доступа, нет материала; первый отказ каждого вида печатается в `console.warn` с телом). Тег шага
раньше назывался `flow`; теперь `flow` — поток смеси (см. ниже).

- `battle_endings` (счётчик с тегом `reason`): `finished` — матч сыгран до последнего раунда, `closed` — комната закрылась раньше
  (отмена, отказ, истекло приглашение или комната на сервере), `abandoned` — через 5 минут матч ещё шёл, скрипт отменил / сдался,
  `poll_failed` — опрос ответил не JSON. `flow_completed` считает `finished` и `closed` одинаково (оба завершают поток); для качества
  игрового опыта смотреть долю `closed`. В сводке `battle.js` и смеси — отдельными строками `battle_endings{reason:...}`.
- `assignments_requested` (доля): открытия главной, которые спросили `GET /assignments`. Клиент спрашивает список только если
  `/today` не сказал `assignments_possible: false` (поля нет у старого сервера — спрашивает как раньше); ученики `load:tokens` ни в одной
  группе не состоят, поэтому у них доля ≈ 0, а `GET /assignments` на просмотре не нагружается.

- `p95 < 300 мс` — горячие запросы (ответ игры / практики / баттла, опрос, раунд, review тренировки). `game_start`, `practice_open`,
  `battle_invite` строят снимок материала — стартовый порог **600 мс**; это догадка до первого замера на железе, поправить по результату.
- `training_distractor_cards` (`rate > 0.3`): доля карточек с вариантами. Ниже — карточки не зрелые (сид не запускали или due кончились), а
  значит замер снова про лёгкий путь.
- Звук (`game_audio`, `practice_audio`): 404 / 503 считаются отдельно (`audio_missing`), не как ошибка сервера — на стенде может не быть клипов.

## Темп (оценка аудита `docs/AUDIT_2026-11-10_RU.md` §2, запросов в минуту на активного ученика)

| Активность | Запросов / мин | Как держится |
|---|---|---|
| тренировка | ~13–20 | думает 3–6 с над карточкой |
| игра, практика | ~10–40 | думает 2–5 с над элементом |
| баттл | ~40 | пара опрашивает каждые 5 / 3 / 2 с (`POLL_INTERVAL_MS` в `stores/battle.ts`: приглашение / комната / отсчёт и игра), плюс раунд и ответ |

Все запросы, кроме опроса баттла и звука, делят лимитер `twa-api` (60 в минуту на ученика): при `THINK_SCALE=1` скрипты его не задевают.
`THINK_SCALE=0.5` удваивает нагрузку на ученика (и может дать 429 — это сигнал, что сценарий слишком быстрый).

## Размеры

- `twa-training-mature.js`, `mixed-profile.js`: `TARGET_VUS` = число учеников (умолчание 1250; в токен-файле столько же).
- `game-caravan.js`, `practice-session.js`: `TARGET_VUS` по умолчанию **300** при запуске через `make` (задать явно: `make load-test-game TARGET_VUS=600`).
- `battle.js`: `TARGET_PAIRS` пар (умолчание 100); 1 VU = 1 пара (играет за обоих по тактам), токен-файл — не меньше `2 × TARGET_PAIRS`
  учеников: `make load-tokens TARGET_VUS=200`. `BATTLE_MODE` = `collocation` (умолчание) | `sentence` | `dictation` | `pairs`.
- `HOLD` — удержание на пике (умолчание `10m`; длительность k6: `10m`, `1h`, `1h30m`), `CARDS_PER_SESSION` — карточек за сессию тренировки (8).
- Срок токенов: `setup()` каждого сценария требует, чтобы токены жили весь запланированный прогон — разгон 8 мин + `HOLD` + спад 1 мин
  + `gracefulRampDown` (30 с, у баттла и смеси 120 с) + 5 мин запаса, но не меньше 30 мин. При `HOLD=10m` это 30 мин (пол), при
  `HOLD=1h` — 76 мин: прогон с токенами на час откажет на старте, а не упадёт посередине. Токены `make load-tokens` живут
  `TOKENS_TTL` секунд (умолчание 7200 = 2 ч, максимум 86400): для удержания дольше ~1,5 ч выпустить их с большим сроком,
  например `make load-tokens TARGET_VUS=1250 TOKENS_TTL=14400`.

## Смешанный профиль

`mixed-profile.js` запускает потоки тренировки, игры, практики, баттла и (при `MIX_BROWSE > 0`) просмотра рядом. Доли учеников (`TARGET_VUS` — все активные; сумма
долей меньше 1 — остаток простаивает, больше 1 — k6 останавливается до старта):

| Переменная | Умолчание | Итерация по коду (`flows.js`, `THINK_SCALE=1`) | Запросов / мин на ученика |
|---|---|---|---|
| `MIX_TRAINING` | 0.45 | open + 8 review + finish = 10 запросов; паузы 8 × 4,5 с + 3,5 с = 39,5 с | ≈ 15,2 |
| `MIX_GAME` | 0.20 | карта + старт + ~4 ответа (угадывающий теряет 3 фляги) + итог = 7; паузы 2 + 4 × 3,5 + 5,5 = 21,5 с | ≈ 19,5 (+ звук `listen`) |
| `MIX_PRACTICE` | 0.20 | хаб + старт + 5 ответов (`collocation`) = 7; паузы 2 + 5 × 3,5 + 5,5 = 25 с | ≈ 16,8 (диктант: + звук на элемент) |
| `MIX_BATTLE` | 0.15 | на **пару**: ~79 запросов (подготовка 4, приглашение и комната ~13, 5 раундов × (4 такта × 2 опроса + 2 раунда + 2 ответа) = 60, итог 2) за ~67 с (матч ~60 с + паузы 7 с) | ≈ 35 |
| `MIX_BROWSE` | **0** | `browse()`: главная + профиль + курсы + хаб практики + каталог = 5 запросов (участник группы — 6, с `/assignments`); паузы 1 + 4 × 2 = 9 с | ≈ 33 (≈ 40 у участника группы) |

Паузы — средние значения `think()`; время ответа сервера в них не входит, поэтому на медленном сервере итерации длиннее и запросов
меньше. Отсюда **предполагаемый спрос** при 1250 учениках:

```
1250 × (0,45 × 15,2 + 0,20 × 19,5 + 0,20 × 16,8 + 0,15 × 35) / 60 = 1250 × 19,35 / 60 ≈ 400 запросов в секунду
```

(опросы баттла уже входят в его ~35 в минуту; прежние «≈ 470» были арифметической ошибкой, по округлённым темпам аудита 16/20/20/40
выходит ≈ 442).

**Просмотр в смеси.** `MIX_BROWSE` по умолчанию 0 — стандартная смесь и её распределение остаются прежними. Предлагаемая смесь с
просмотром — 15 % просмотра, остальные доли × 0,85 (с округлением):

```bash
make load-test-mixed BASE_URL=https://<staging> TARGET_VUS=1250 \
  MIX_TRAINING=0.38 MIX_GAME=0.17 MIX_PRACTICE=0.17 MIX_BATTLE=0.13 MIX_BROWSE=0.15
# спрос: 1250 × (0,38 × 15,2 + 0,17 × 19,5 + 0,17 × 16,8 + 0,13 × 35 + 0,15 × 33,3) / 60 ≈ 448 запросов в секунду
```

Учтите: VU просмотра ходит по экранам **без перерыва** (как итерация `twa-hot-paths.js` без тренировки), ≈ 33 запроса в минуту — это
верхняя оценка «листающего» ученика, а не среднего. Это оценка нагрузки, которую генератор **должен** дать, а не ёмкость: в отчёт о ёмкости идёт измеренный
`http_reqs` в секунду на устойчивой ступени (окно удержания), рядом — число обслуженных учеников и доля завершённых занятий
(`flow_completed`).

**Кто что играет** (`plan.js`: `allocateMix`, `mixSlot`). Доли округляются методом наибольшего остатка: сначала каждый поток берёт
целую часть своей квоты (баттл — целые пары), затем оставшиеся до `floor(TARGET_VUS × сумма долей)` ученики по одному идут потоку с
наибольшей недостачей (пара — только если осталось двое). Поэтому участников **никогда не больше `TARGET_VUS`**, и токен-файла из
`TARGET_VUS` учеников хватает. Файл режется на непересекающиеся диапазоны: сначала пары баттла (индексы 0-1, 2-3, … — это пары
друзей сида 1-2, 3-4, …), затем тренировка, игра, практика, просмотр. При 1250 и долях по умолчанию:

| Поток | Учеников | VU | Индексы токенов |
|---|---|---|---|
| баттл | 188 (94 пары) | 94 | 0–187 |
| тренировка | 562 | 562 | 188–749 |
| игра | 250 | 250 | 750–999 |
| практика | 250 | 250 | 1000–1249 |
| всего | 1250 | 1156 | |

С предлагаемой смесью с просмотром (0.38 / 0.17 / 0.17 / 0.13 / 0.15; квоты 475 / 212,5 / 212,5 / 162,5 / 187,5 — два оставшихся
ученика достаются игре и практике по порядку потоков):

| Поток | Учеников | VU | Индексы токенов |
|---|---|---|---|
| баттл | 162 (81 пара) | 81 | 0–161 |
| тренировка | 475 | 475 | 162–636 |
| игра | 213 | 213 | 637–849 |
| практика | 213 | 213 | 850–1062 |
| просмотр | 187 | 187 | 1063–1249 |
| всего | 1250 | 1169 | |

`setup()` печатает это распределение в начале прогона. `MIX_BATTLE=0` — пар и пула нет, тренировка начинается с индекса 0.
Просмотр в порядке потоков последний: при `MIX_BROWSE=0` все остальные получают ровно то же, что и без него (это проверяет тест).

Смесь — **один** сценарий k6 (`mixed`, `ramping-vus` до числа VU, `gracefulRampDown` 120 с), а поток выбирается по номеру VU:
k6 нумерует VU сквозь все сценарии в порядке их запуска, и у параллельных сценариев номера перемешиваются, поэтому «n-й VU
сценария» по `__VU` не узнать (прежняя формула `(__VU - 1) % pairs` могла дать двум VU одну пару). Номера 1..N раздаются потокам по
очереди в их долях (на каждом префиксе доля потока отклоняется не больше чем на одного VU), n-й номер потока берёт n-го ученика
(n-ю пару) его диапазона. Каждому номеру — свой слот, так что при любом порядке запуска VU один ученик не играется двумя VU; если
k6 запускает младшие номера первыми, разгон 20 % → 50 % → 100 % ещё и держит пропорции смеси (на удержании они точные всегда).

**Разбивка по потокам.** Каждый запрос и каждая своя метрика итерации смеси несут тег `flow` (`training` | `game` | `practice` |
`battle` | `browse`) — тег VU (`exec.vu.metrics.tags`, в старых k6 `exec.vu.tags`), его ставит `mixed-profile.js` в начале итерации. В
пороги добавлены «пустые» (всегда проходящие) подметрики `http_reqs{flow:…}`, `http_req_duration{flow:…}`, `flow_completed{flow:…}` и
`battle_endings{reason:…}`: k6 печатает подметрику в итоговой сводке (и в `--summary-export`) только если на неё есть порог. Так сводка
сразу делится по потокам; в выводе `--out` тег `flow` есть у каждой точки.

**Как считать учеников.** Один VU баттла играет за **двоих**: VU смеси = учеников − пар (1156 при 1250). Число активных учеников —
`TARGET_VUS` (точнее, сумма столбца «учеников» выше); `flow_completed` у баттла — один матч на двоих. Для сравнения ёмкости по
ученикам считать успешные действия (`training_cards_served`, `game_answers`, `practice_answers`, `battle_answers`) и участников, а
не итерации.

**Ступени: отдельный прогон на каждую цель.** Для 100 / 300 / 600 / 1250 активных учеников — отдельный запуск, следующий — только
если предыдущий прошёл пороги:

```bash
make load-tokens TARGET_VUS=1250 && make load-seed     # один файл на все ступени: меньшая цель берёт начало файла
for n in 100 300 600 1250; do make load-test-mixed BASE_URL=https://<staging> TARGET_VUS=$n HOLD=10m || break; done
# отчёты: tests/load/k6/results/mixed-profile-<n>-summary.json
```

Каждый прогон сам разгоняется 20 % → 50 % → 100 % цели за 8 минут, держит `HOLD` и спадает. Сравнивают **окно удержания** (последние
`HOLD` минут перед спадом): p95/p99, `http_reqs`/с, 429/5xx — по временным рядам (метрики стенда в Grafana; у k6 —
вывод `--out`, через `make` он не подключён), а не по сводке за весь прогон: в сводке разгон разбавляет задержки пика. Между ступенями — `make load-seed` («перезарядить» карточки), если
`training_review_coverage` падает. Просмотр главной и каталога в стандартной смеси выключен (`MIX_BROWSE=0`); включать его — см. выше.

## Всплеск открытий (`arrival-burst.js`)

Рассылка бота или объявление в группе класса: много учеников нажимают кнопку в течение минуты. Остальные сценарии держат **фиксированное
число VU**, а VU ждёт ответа, прежде чем послать следующий запрос: когда сервер замедляется, генератор замедляется вместе с ним и
нагрузка сама спадает — пик открытий так не воспроизвести. Здесь открытия **поступают с заданным темпом** (`ramping-arrival-rate`)
независимо от того, как отвечает сервер. Использовать: для репетиции рассылки / объявления, для проверки холодного кэша главной под
напором и для поиска темпа, при котором открытия начинают теряться; для «вечера в целом» — смесь.

| Переменная | Умолчание | Что значит |
|---|---|---|
| `BURST_RATE` | 20 | открытий в секунду на пике (целое) |
| `BURST_RAMP` | `30s` | разгон от 0 до `BURST_RATE` (линейно) |
| `HOLD` | `2m` | удержание пика |
| `CLASS_SHARE` | 0.2 | доля открытий «по объявлению класса» (0…1, равномерно по прогону) |
| `BURST_PREALLOCATED_VUS` | `max(10, 2 × BURST_RATE)` | VU, заготовленные до старта |
| `BURST_MAX_VUS` | `max(50, 10 × BURST_RATE)` | потолок VU (не меньше заготовленных) |
| `BURST_MAX_DROPPED` | 0 | порог `dropped_iterations` (`count<=`) |

**Итерация = одно открытие одного ученика**, без пауз:

- самостоятельный ученик (`1 − CLASS_SHARE`): `GET /today`, затем `GET /assignments` — только если `/today` не сказал
  `assignments_possible: false` (как клиент, `stores/assignments.ts`), затем `GET /me`;
- участник класса по ссылке объявления (`/twa/?from=assignment&lesson=<id>`): устройство помнит «может быть», поэтому `/today` и
  `/assignments` идут параллельно, затем `GET /me` и сразу открытие урока (`POST /training/sessions`, `mode: lesson`,
  `source: assignment`): первое незавершённое задание из списка, а если список пуст — первый урок курса токен-файла.

**Чего не хватает сида.** `LoadScenarioSeeder` не создаёт центров, групп и заданий: на стенде, подготовленном только `make load-seed`,
`/today` у всех учеников говорит `assignments_possible: false`, а список заданий пуст. Поэтому путь класса проверяет параллельный
запрос списка (пустого) и открытие урока, но не чтение непустого списка и не проверку доступа к уроку центра. Доля открытий класса,
где задание нашлось, — `burst_assignment_found` (0 на таком стенде). Для полного пути нужен сид центра с группой, связанной с чатом,
членством учеников `load:tokens` и активным заданием.

**Токены.** Открытие с номером i (`exec.scenario.iterationInTest`, уникален в прогоне) играет ученик i mod (размер файла): ученик
открывает снова только после всех остальных, то есть не раньше чем через 60 с на полном темпе (`plan.js`: `burstToken`, `burstPool`).
`setup()` требует `min(планируемых открытий, 60 × BURST_RATE)` учеников — 1200 при умолчаниях (`make load-tokens TARGET_VUS=1250`
хватает; при `BURST_RATE=50` нужно 3000) — и чтобы токены жили весь прогон (разгон + удержание + 30 с, не меньше 30 мин). Открытий
при умолчаниях: 20 × 30 / 2 + 20 × 120 = 2700.

**Пороги:** p95 < 300 мс у `today`, `assignments`, `me` и (при `CLASS_SHARE > 0`) `training_open`; 5xx и 429 — ноль; `checks > 99 %`,
`http_req_failed < 1 %`; `dropped_iterations` не больше `BURST_MAX_DROPPED`.

**Как читать `dropped_iterations`.** Это открытия, которые k6 должен был начать по расписанию, но не смог: все VU заняты, а `maxVUs`
исчерпан. Такие открытия **не отправляются позже** — сервер их не видел. Причины две: сервер отвечает медленнее, чем рассчитано
(открытие длится дольше, VU освобождаются реже — смотреть p95/p99 и `vus` в сводке), или потолок VU мал для темпа (`vus_max`
упёрся в `BURST_MAX_VUS` при нормальных задержках — поднять `BURST_MAX_VUS` и повторить). Ненулевое значение при нормальных задержках —
проблема генератора, при растущих — признак, что темп выше ёмкости. Фактический темп — `iterations` в секунду в сводке, а не `BURST_RATE`.

```bash
make load-tokens TARGET_VUS=1250
make load-test-burst BASE_URL=https://<staging> BURST_RATE=20 HOLD=2m CLASS_SHARE=0.2
# отчёт: tests/load/k6/results/arrival-burst-20-summary.json
```

**Вне нагрузки остаётся вход.** Токены выпущены заранее (`load:tokens`), поэтому `POST /api/twa/auth` — проверка HMAC `initData` и
его лимитер — не нагружаются ни этим, ни другими сценариями. При реальном всплеске каждое открытие с холодного устройства начинается с
него.

## Что проверено без k6 и Docker

Арифметика сценариев (распределение смеси, диапазоны токенов, пары, срок токенов) вынесена в `plan.js` без импортов k6 и
проверяется встроенным раннером Node (без зависимостей): `make load-plan-test` = `node --test tests/load/k6/plan.test.js` —
стандартная смесь 1250, смесь из пяти потоков с просмотром, `MIX_BROWSE=0` без изменений распределения, малые нечётные пулы, доля
баттла 0, сумма долей меньше и больше 1 и перебор `TARGET_VUS` 0..1400 (участников не больше пула, диапазоны не пересекаются, пары не
повторяются и начинаются с чётного индекса); для всплеска — число открытий, VU, выбор токенов (ни один ученик не открывает дважды
быстрее чем за 60 с) и равномерная доля открытий класса.

Скрипты написаны под k6 1.x (ES-модули, `k6/http`, `k6/metrics`, `k6/data`). В окружении, где они писались, не было ни `k6`, ни Docker, поэтому
`k6 inspect` не запускался: каждый файл прошёл `node --check`, а потоки (`flows.js`, сценарии, включая `setup()`; `arrival-burst.js`
и просмотр в смеси — так же) были прогнаны под Node с заглушками модулей k6 против временного мок-сервера API (форма запросов/ответов — по Form Request и Resource-классам
проекта). Это проверяет логику циклов и формы тел, но не пороги и не настоящее поведение API: первый прогон на staging может потребовать правок
(в первую очередь — стартовых порогов 600 мс и формы `current` у режимов практики).

Без настоящего k6 не проверено: что `exec.vu.metrics.tags` (или `exec.vu.tags`) действительно добавляет тег `flow` ко всем точкам VU в
k6 1.0 (в заглушке — да); что «пустые» пороги `count>=0` / `max>=0` / `rate>=0` выводят подметрики в сводку; поведение порога
`dropped_iterations` при отсутствии пропусков (метрика без точек) и само расписание `ramping-arrival-rate` (`startRate: 0`, этап `0`
при `HOLD=0`).
