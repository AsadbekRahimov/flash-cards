# k6: нагрузочные сценарии LexiFlow

Запускаются на **staging** (не на проде: `load:tokens` и сид отказываются работать при `APP_ENV=production`), из образа
`grafana/k6` через `make`; ничего не ставится. Общий порядок и пороги приёмки — `docs/STAGING_PHASE2_CHECKLIST.md` §7.3.

| Файл | Что нагружает | Команда |
|---|---|---|
| `twa-hot-paths.js` | Главная, профиль, курсы, каталог, тренировка **со свежими** карточками (все flash) | `make load-test` |
| `twa-training-mature.js` | тренировка со **зрелыми** карточками: meaning / reverse / audio (варианты с дистракторами строит сервер; ответ — один из вариантов), у Pro — ввод (spelling / gap-fill) | `make load-test-mature` |
| `game-caravan.js` | игра «Караван»: карта, старт забега, ответы до конца, итог | `make load-test-game` |
| `practice-session.js` | практика: сессия одного режима (`PRACTICE_MODE`) от хаба до последнего ответа | `make load-test-practice` |
| `battle.js` | баттл: пара учеников от приглашения до результата, опрос 5 с / 3 с / 2 с | `make load-test-battle` |
| `mixed-profile.js` | всё вместе в долях по оценке аудита | `make load-test-mixed` |
| `telegram-webhook.js` | вебхук Telegram | `make load-test-webhook` |
| `flows.js`, `lib.js` | общие функции (не запускаются) | |

## Подготовка (один раз на стенд, повторять по мере надобности)

```bash
make load-tokens TARGET_VUS=1250      # тестовые ученики Load1..LoadN и их JWT -> tests/load/k6/tokens.json (0600)
make load-seed                        # зрелые карточки + пилот практики + пары друзей (1-2, 3-4, ...)
```

`make load-seed` = `php artisan db:seed --class=LoadScenarioSeeder --force` (`database/seeders/LoadScenarioSeeder.php`), работает
только с учениками с меткой `meta.load_test` (их создаёт `load:tokens`), в окружениях `local | testing | staging`:

- каждому — строки `word_repetitions` для первых `LOAD_SCENARIO_WORDS` (умолчание 300) активных слов курса: состояние `review`,
  `repetitions` циклом 2..7, **срок наступил**. Так селектор упражнений отдаёт flash / reverse / audio, на каждом третьем проходе
  (3, 6) — ввод (только у Pro: `exercise.spelling` / `exercise.gap_fill`; у Free эти карточки заменяются на rotate). Это же даёт доступ
  к практике / игре / баттлу — задание выдаётся ученику, «знакомому» со всеми его словами;
- `practice_pilot_at` (для стенда с `PRACTICE_ACCESS=pilot` / `GAME_ACCESS=pilot`);
- дружба внутри пар (1-2, 3-4, ...) через `FriendshipService`.

Повторный запуск идемпотентен и **снова делает карточки «наступившими»** — так «перезаряжают» учеников после долгого прогона
(иначе дневной обзор кончится: `training_review_coverage` < 0.9). `LOAD_SCENARIO_COURSE=<slug>` — другой курс. Чтобы у ученика была
карточка ввода, ему нужен Pro (выдать через админку / подписку); без Pro сценарий всё равно проходит путь с дистракторами.

Настройки стенда (`.env` staging), без которых сценарии упираются в лимиты Free и это видно в `flow_aborted`:

```dotenv
PRACTICE_ACCESS=all
PRACTICE_FREE_SESSIONS_PER_DAY=        # пусто = без лимита для Free (умолчание 2 в день)
PRACTICE_FREE_BATTLES_PER_DAY=         # умолчание 1 в день
GAME_ACCESS=all
GAME_FREE_RUNS_PER_DAY=                # умолчание 1 в день
```

Нужен опубликованный контент практики (`php artisan practice:import <файл> --publish`) и, для диктанта, его аудио.

## Как отвечают скрипты

API **не отдаёт правильные ответы** (docs/16 §12), а k6 не ходит в БД стенда (браузерный e2e `resources/twa/scripts/e2e` читает снимок
сессии из SQLite — удалённому стенду такое недоступно). Поэтому ученик в k6 **угадывает**: `answerFor()` в `lib.js` строит ответ по
тому, что показывает API (`options` → случайный `option_id`, `fragments` → перемешанный `order`, пары → `left_id`/`right_id`,
ввод → `test`). Сервер делает ту же работу для неверного ответа, что и для верного (оценка, снимок, состояние, счётчики) — это и
измеряется. Следствие: забег «Каравана» у угадывающего часто кончается, когда фляги вышли, а не на последнем элементе; оба конца
считаются завершением (`flow_completed`).

## Метрики и пороги

Общие: `server_errors` (любой 5xx — провал), `rate_limited` (429 — провал: сценарий быстрее лимитеров, а не сервер медленный),
`checks > 99 %`, `http_req_failed < 1 %`, `flow_completed > 95 %` (прогон дошёл до естественного конца: сессия закрыта, забег окончен,
матч закрыт), `flow_aborted` (с тегами `flow` и `status`: отказ API — лимит, нет доступа, нет материала; первый отказ каждого
вида печатается в `console.warn` с телом).

- `p95 < 300 мс` — горячие запросы (ответ игры / практики / баттла, опрос, раунд, review тренировки). `game_start`, `practice_open`,
  `battle_invite` строят снимок материала — стартовый порог **600 мс**; это догадка до первого замера на железе, поправить по результату.
- `training_distractor_cards` (`rate > 0.3`): доля карточек с вариантами. Ниже — карточки не зрелые (сид не запускали или due кончились), а
  значит замер снова про лёгкий путь.
- Звук (`game_audio`, `practice_audio`): 404 / 503 считаются отдельно (`audio_missing`), не как ошибка сервера — на стенде может не быть клипов.

## Темп (оценка аудита `docs/AUDIT_2026-11-10_RU.md` §2, запросов в минуту на активного ученика)

| Активность | Запросов / мин | Как держится |
|---|---|---|
| тренировка | ~13–20 | думает 3–6 с над карточкой |
| игра, практика | ~10–40 | думает 2–5 с над элементом |
| баттл | ~40 | пара опрашивает каждые 5 / 3 / 2 с (`POLL_INTERVAL_MS` в `stores/battle.ts`: приглашение / комната / отсчёт и игра), плюс раунд и ответ |

Все запросы, кроме опроса баттла и звука, делят лимитер `twa-api` (60 в минуту на ученика): при `THINK_SCALE=1` скрипты его не задевают.
`THINK_SCALE=0.5` удваивает нагрузку на ученика (и может дать 429 — это сигнал, что сценарий слишком быстрый).

## Размеры

- `twa-training-mature.js`, `mixed-profile.js`: `TARGET_VUS` = число учеников (умолчание 1250; в токен-файле столько же).
- `game-caravan.js`, `practice-session.js`: `TARGET_VUS` по умолчанию **300** при запуске через `make` (задать явно: `make load-test-game TARGET_VUS=600`).
- `battle.js`: `TARGET_PAIRS` пар (умолчание 100); 1 VU = 1 пара (играет за обоих по тактам), токен-файл — не меньше `2 × TARGET_PAIRS`
  учеников: `make load-tokens TARGET_VUS=200`. `BATTLE_MODE` = `collocation` (умолчание) | `sentence` | `dictation` | `pairs`.
- `HOLD` — удержание на пике (умолчание `10m`), `CARDS_PER_SESSION` — карточек за сессию тренировки (8).

## Смешанный профиль

`mixed-profile.js` запускает потоки тренировки, игры, практики и баттла рядом. Доли учеников (`TARGET_VUS` — все активные):

| Переменная | Умолчание | Запросов / мин на ученика |
|---|---|---|
| `MIX_TRAINING` | 0.45 | ~16 |
| `MIX_GAME` | 0.20 | ~20 |
| `MIX_PRACTICE` | 0.20 | ~20 (режим `PRACTICE_MODE`) |
| `MIX_BATTLE` | 0.15 | ~40 (число пар = доля × `TARGET_VUS` / 2) |

При 1250 учениках это ≈ 28 000 запросов в минуту ≈ 470 в секунду на сервере (без опросов баттла сверх нормы). Участники баттла берутся с
**конца** токен-файла (пары сида 1-2, 3-4, …), остальные — с начала: один ученик не играется двумя VU. Если токенов не хватает,
`setup()` останавливает прогон и называет число для `make load-tokens`. Браузинг из `twa-hot-paths.js` в смесь не входит —
его гоняют отдельно (лёгкий путь).

## Что проверено без k6 и Docker

Скрипты написаны под k6 1.x (ES-модули, `k6/http`, `k6/metrics`, `k6/data`). В окружении, где они писались, не было ни `k6`, ни Docker, поэтому
`k6 inspect` не запускался: каждый файл прошёл `node --check`, а потоки (`flows.js`, все пять сценариев, включая `setup()`) были
прогнаны под Node с заглушками модулей k6 против временного мок-сервера API (форма запросов/ответов — по Form Request и Resource-классам
проекта). Это проверяет логику циклов и формы тел, но не пороги и не настоящее поведение API: первый прогон на staging может потребовать правок
(в первую очередь — стартовых порогов 600 мс и формы `current` у режимов практики).
